## 1. 問題與論點(摘要,完整版見 `AI深化方向.md`)

1. 太空任務需要機上自主判斷;地面監控受下行排程限制【已查證:Telemanom 論文配合 SMAP 每 70 分鐘下行】
2. 傳統 FDIR 靠門檻,認不出緩慢劣化與未知故障【已查證:arXiv 2604.08424】
3. 機上 ML 卡在信任、認證、可解釋性,而且主流 ML 工具太重【已查證:arXiv 2604.08424、SmallSat 2026 mlpack 論文】
4. ML 元件本身會卡住、吃光 CPU、當掉,飛行軟體不能跟著掛

**論點**:QNX 的微核心隔離、即時排程、行程監控重啟,正好把 3、4 點變成可以工程化處理的問題。**AI 是存在的理由,QNX 讓它可以被部署。**

**產業標準對照**(讓評審看到我們懂這個領域):
- **ECSS FDIR 分層**:第 0–2 層自主修復、第 3 層 safe mode、第 4 層 survival mode【已查證:Thales Alenia Space 簡報】
- **ECSS 機上自主等級**:E2 為地面預排程序,E3 為事件驅動的機上自適應操作【已查證:2021 論文整理的 ECSS-E-ST-70-11C 表格;Rev.1 已於 2025-10 發布】
- **ASTM F3269-21 Run-Time Assurance**:讓「複雜功能」(本案的 ML)與確定性的「恢復功能」並存,由安全監視器切換;標準建議恢復邏輯越簡單越好,而且同一任務中反覆觸發恢復,代表複雜功能可能有問題【已查證:ASTM 商店頁與 DLR 論文摘要】

## 3. 系統架構

### 3.1 Repo 結構

F Prime 官方慣例是平台函式庫和參考專案各一個 repo(fprime-vxworks + fprime-vxworks-reference)【已查證】。但 Devpost 只收一個 repo URL,而規則要求「repo 包含所有原始碼」,所以**比賽期間合併成單一 repo**,賽後再依官方慣例拆開、申請轉移到 fprime-community。

```
fprime-qnx/                         (新 repo,Apache-2.0)
├── lib/fprime/                     → git submodule:nasa/fprime @ v4.4.2
├── FprimeQnx/                      ← 平台函式庫(移植本體)
│   ├── cmake/
│   │   ├── platform/QNX.cmake      平台檔:選用 Posix 實作 + QNX 專屬實作
│   │   └── toolchain/qnx-x86_64.cmake, qnx-aarch64le.cmake
│   ├── Os/                         QNX OSAL:Cpu、Memory、RawTime、Task 擴充
│   ├── Svc/QnxTimer/               pulse 驅動的 rate group 定時器
│   ├── Drv/QnxMsgDriver/           GenericHub 的 QNX message passing 傳輸層
│   ├── Svc/QnxCpuBudget/           CPU-time timer 預算監看
│   └── config/PlatformCfg.fpp      handle 大小等平台設定
├── FprimeQnxReference/             ← 參考專案
│   ├── FlightDeployment/           Process 1:飛行軟體
│   ├── MlDeployment/               Process 2:機上 ML
│   ├── Components/                 任務元件(第 3.3 節)
│   └── test/int/                   官方整合測試 + 本案測試
├── ml/                             主機端訓練、特徵、資料集腳本
├── qnx/                            SLM 設定、secpol 政策、mkqnximage 選項
├── experiments/                    故障注入腳本、量測結果、圖表

└── docs/                           架構、QNX 證據索引、決策紀錄
```

### 3.2 執行期架構

```
WSL2 Ubuntu 24.04(主機)                 QEMU x86_64 + KVM(QNX 8.0 精簡映像,無圖形介面)
┌─────────────────┐   TCP(virbr0 橋接)  ┌──────────────────────────────────────────────┐
│ F Prime GDS     │◄──────────────────►│ slm(System Launch and Monitor)               │
│ (網頁地面站)     │                     │  ├─ FlightSW   [secpol type: fsw_t]  critical │
│ 指令 / 遙測 /    │                     │  │   QnxTimer → RateGroups(SCHED_FIFO 高)      │
│ 事件 / 圖表      │                     │  │   AdcsSim、FeatureExtractor、RecoveryGate  │
└─────────────────┘                     │  │   CmdDispatcher、TlmChan、EventManager      │
                                        │  │   GenericHub ─ QnxMsgDriver(server)        │
                                        │  │        ▲ MsgSend / MsgReceive / MsgReply   │
                                        │  │        ▼  (name_attach "fprime/hub")        │
                                        │  └─ MlAdvisor  [secpol type: ml_t]  repair=restart
                                        │      GenericHub ─ QnxMsgDriver(client)        │
                                        │      FfnClassifier、KdeNovelty、Explainer     │
                                        │      RecoveryAdvisor                          │
                                        │      SCHED_SPORADIC 預算 + QnxCpuBudget 監看   │
                                        └──────────────────────────────────────────────┘
```

**設計重點**
- **兩個 F Prime deployment、兩個行程**,用官方 GenericHub 串接。官方多核心指南在 Linux 上用 named message queue 或 pipe 當傳輸層【已查證】,我們換成 QNX message passing
- **飛行軟體標記為 critical**:它一死系統就重啟,符合「飛行軟體是最後防線」
- **ML 設 `repair=restart`**:ML 死掉由 SLM 自動重啟,支援 backoff【已查證:QNX 8.0 slm 文件 `<SLM:repair>`】
- **secpol**:ML 行程的型別只能連到 hub channel,不能連其他系統服務【已查證:QNX 8.0 `allow X Y:channel connect` 語法;具體規則**待驗證**】

### 3.3 元件清單

**A. 平台層(移植本體,`FprimeQnx/`)**

| 元件 | 做什麼 | 為什麼需要 | 依據 |
|---|---|---|---|
| `QNX.cmake` 平台檔 | 選用 Posix OSAL + QNX 專屬實作、定義 `TGT_OS_TYPE_QNX` | F Prime 的 Linux 平台檔只是「Posix + Linux 版 Cpu/Memory」【已查證】,QNX 比照 | `cmake/platform/Linux.cmake` |
| qcc 工具鏈檔 | x86_64 與 aarch64le | 沿用 qnx-ports 的 `qnx.nto.toolchain.cmake` 寫法,改用環境變數、不寫死路徑 | qnx-ports/build-files;F Prime 官方提醒不要寫死路徑【已查證】 |
| `Os::Cpu`(QNX) | 回報各 CPU 使用率 | Linux 版讀 `/proc/stat`,**QNX 沒有這個檔**。而官方 mlpack 參考實作偵測的正是 CPU 使用率遙測,沒有它就跑不起來 | `Os/Linux/Cpu.cpp`【已查證】;QNX 做法**待驗證**(候選:讀各核 idle thread 的執行時間) |
| `Os::Memory`(QNX) | 回報總量與可用記憶體 | Linux 版用 `sysinfo()`,QNX 沒有 | `Os/Linux/Memory.cpp`【已查證】;QNX 做法**待驗證** |
| `Os::RawTime`(QNX,選用) | 用 `ClockCycles()` 做高解析度計時 | 量測 rate group 執行時間 | **待驗證** |
| `Os::Task` 擴充 | CPU 綁核(runmask)、可選 SCHED_SPORADIC | Posix 版固定用 SCHED_RR【已查證】,不能設 sporadic 或綁核 | `Os/Posix/Task.cpp` |
| `Svc::QnxTimer` | 用 `timer_create` + **pulse** 驅動 rate group | Linux 版 `LinuxTimer` 用 `timerfd`(QNX 沒有);另一個實作 TaskDelay 會累積誤差【已查證】 | `Svc/LinuxTimer/` |
| `Drv::QnxMsgDriver` | 實作 `ByteStreamDriver` 介面,底層用 `name_attach` / `MsgSend` / `MsgReceive` / `MsgReply` | GenericHub 要搭配實作 ByteStreamDriver 的驅動 + `ByteStreamBufferAdapter`【已查證】 | `Svc/GenericHub/GenericHub.fpp`、`Drv/Interfaces/ByteStreamDriver.fpp` |
| `Svc::QnxCpuBudget` | 對 ML 執行緒的 CPU-time clock 設 timer,超過預算就發事件並終止 | QNX 8.0 **不支援** adaptive partitioning【已查證】;官方建議改用 sporadic 排程與 per-thread runtime clock | QNX 8.0「Monitoring execution times」【已查證:可對 thread CPU-time clock 建 timer;每個 clock 只能掛一個 timer】 |

> **關於 `Os::Queue` 的設計決定**:F Prime 的佇列是**非同步**的(送出就返回),QNX `MsgSend` 是**同步**的(送出後阻塞到對方回覆),語意不合。所以行程內佇列沿用官方 Generic PriorityQueue,QNX message passing 用在語意吻合的地方:**跨行程 hub**(請求/回覆)。這也是要寫進 Devpost 的工程判斷,展示「懂得何時用、何時不用」。

**B. 任務層(`FprimeQnxReference/Components/`)**

| 元件 | 所在行程 | 做什麼 |
|---|---|---|
| `AdcsSim` | FlightSW | 模擬姿態控制感測器組(3 軸磁力計 + 6 個光電二極體,**正好是 OPS-SAT 資料集的 9 個通道**【已查證】)。兩種模式:① 回放 OPSSAT-AD 真實遙測段;② 注入故障(卡值、偏移、雜訊、斷訊)。會回應恢復指令(例如排除某個光電二極體、重置磁力計) |
| `FeatureExtractor` | FlightSW | 每段遙測計算論文定義的 18 個手工特徵(平均、變異、峰度、偏度、峰值數、差分變異……)【已查證:dataset.csv 欄位】。確定性 C++,經 hub 送給 ML |
| `FfnClassifier` | MlAdvisor | mlpack 前饋神經網路(論文最佳模型為 FCNN)【已查證:AUC-PR 0.979】,辨識**已知型態**的異常 |
| `KdeNovelty` | MlAdvisor | 延伸官方 `KDEAnomalyDetector`(mlpack KDE)【已查證】,對特徵做密度估計,抓**沒見過的異常** |
| `Explainer` | MlAdvisor | 遮蔽法(occlusion):逐一遮掉 18 個特徵,看哪幾個最影響判斷,輸出「哪個通道、哪個特徵、偏離多少」。只有 18 個特徵,機上算得起 |
| `RecoveryAdvisor` | MlAdvisor | 依偵測結果提出**建議**(對應 ECSS 分層,見第 4.4 節),附信心度與理由 |
| `RecoveryGate` | FlightSW | **方向 B 的核心**。依 ASTM F3269 RTA 精神做確定性安全監視:只有規則全過才交給 `RecoveryExecutor` 執行 |
| `RecoveryExecutor` | FlightSW | 執行核准的動作;ML 失聯或被隔離時,退回傳統門檻 FDIR |
| `Svc.Health` | 兩邊 | F Prime 官方健康檢查(ping);ML 沒回應就由 Gate 標記「顧問不可用」 |

### 3.4 資料流(一次完整的偵測到恢復)

```
AdcsSim ──遙測──► FeatureExtractor ──18 特徵──► [Hub: QNX MsgSend] ──► FfnClassifier ─┐
                                                                     KdeNovelty    ─┼► Explainer ─► RecoveryAdvisor
GDS ◄── 事件:異常 + 解釋 ◄──────────────────────────────────────────────────────────┘        │
GDS ◄── 事件:核准 / 拒絕(附哪條規則)◄── RecoveryGate ◄── [Hub] ◄── 建議(動作、信心、理由)┘
                                              │ 核准
                                              ▼
                                       RecoveryExecutor ──指令──► AdcsSim(狀態改變,遙測恢復)
```

### 3.5 故障圍堵矩陣(demo 的核心)

| ML 出什麼事 | QNX 怎麼擋 | 飛行軟體看到什麼 | 怎麼證明 |
|---|---|---|---|
| **無窮迴圈** | SCHED_SPORADIC 預算用完降到低優先權;`QnxCpuBudget` 觸發 → 終止 → SLM 重啟 | rate group 沒有 cycle slip;Gate 進入「顧問不可用」,退回門檻 FDIR | rate group 時序遙測 + kernel trace |
| **當掉(segfault / abort)** | 微核心行程隔離;SLM `repair=restart`(含 backoff) | Health ping 失敗 → 標記不可用 → 重啟後自動恢復 | GDS 事件時間軸 |
| **記憶體暴衝** | 行程位址空間隔離;資源上限 | 不受影響 | **待驗證**:QNX 8.0 的 `setrlimit` 支援沒查到官方說明,動工時實測;不行就改用 SLM 監看 + 行程記憶體查詢 |
| **亂給建議(誤報、洗版)** | — (這是邏輯層問題) | Gate 拒絕;同一時窗內反覆觸發 → 隔離顧問(呼應 ASTM F3269「反覆觸發恢復代表複雜功能有問題」) | GDS 事件:拒絕原因 |
| **想直接下指令** | secpol:`ml_t` 只能連 hub channel;Gate 只接受白名單動作 | 不可能繞過 | `secpol -f connect` 輸出 + 嘗試失敗的 log |

### 4.4 方向 B:恢復建議與安全規則

**建議動作表**(對應 ECSS FDIR 分層)

| 偵測情況 | 建議動作 | ECSS 層級 |
|---|---|---|
| 單一光電二極體異常 | 從太陽向量估算中排除該通道 | 第 1–2 層(單元 / 子系統重組) |
| 磁力計某軸卡值或偏移 | 重置磁力計;仍異常則切換備援 | 第 1–2 層 |
| 多通道同時異常、或不明原因 | 進入 safe mode | 第 3 層 |
| 顧問失聯或被隔離 | (不由 ML 建議)Executor 退回門檻 FDIR | — |

**RecoveryGate 規則**(確定性、刻意保持簡單,依 ASTM F3269 建議)
1. **白名單**:只接受上表動作
2. **持續性**:同一異常連續 N 次偵測才受理
3. **限頻**:同一動作在時窗 T 內最多 K 次
4. **狀態約束**:例如至少保留 4 個光電二極體才允許再排除
5. **永遠允許更安全的動作**:進入 safe mode 不受限頻約束
6. **顧問隔離**:時窗內被拒絕超過 M 次 → 隔離 ML,退回門檻 FDIR
7. **全部留紀錄**:每個核准或拒絕都發事件到 GDS,附觸發的規則編號

N、T、K、M 的值在實驗時調整,並記錄到決策紀錄。

## 5. QNX 原生機制對照(Best Use of QNX-specific Technologies)

| 官方列舉的機制 | 用在哪 | 證據形式 |
|---|---|---|
| **Native message passing** | `QnxMsgDriver`(跨行程 hub;client 優先權會傳給 server) | 原始碼 + kernel trace 中的 MsgSend / MsgReceive 事件 |
| **Microkernel architecture** | 飛行軟體與 ML 分屬不同行程;故障圍堵矩陣 | 故障注入實驗 |
| **Real-time services** | `QnxTimer`(timer + pulse)、SCHED_FIFO rate group、SCHED_SPORADIC 的 ML、CPU-time timer 預算 | 時序量測 + trace |
| **Startup / boot customization** | 用 mkqnximage / buildfile 建精簡映像,開機由 SLM 依相依關係啟動兩個行程 | buildfile + SLM 設定檔 |
| **Security policies** | secpol 限制 `ml_t` 只能連 hub | 政策檔 + `secpol -f connect` 輸出 |
| (加分)SLM / HAM | ML 自動重啟、飛行軟體 critical | SLM 設定 + 重啟事件 |

| **Resource managers** | 唯讀的 `/dev/fprime/gate`:`cat` 就能看到顧問狀態、最近的核准或拒絕、被拒次數(D6) | 原始碼 + 影片中的 `cat` 畫面 |

> resource manager **刻意做成唯讀**:如果可寫,等於多一條繞過 F Prime 指令系統、直接改安全閘門的路,跟「所有指令都要經過把關」的論點矛盾。

## 6. 驗證計畫

| 編號 | 驗證項目 | 方法 | 通過標準 |
|---|---|---|---|
| V1 | **OSAL 正確性** | 在 QNX 上跑 F Prime 官方 OSAL 測試(Os/test/ut 的 11 類:condition、countingsemaphore、cpu、directory、file、filesystem、memory、mutex、queue、rawtime、task)與 Posix 測試【已查證:測試存在】 | 全數通過,或每個失敗都有記錄原因 |
| V2 | **參考部署可運作** | 用 GDS 整合測試 API 跑官方整合測試(官方新平台流程要求)【已查證】 | 通過 |
| V3 | **ML 一致性** | 主機與 QNX 對 529 段測試集的預測比對 | 差異在容差內 |
| V4 | **偵測成績** | 第 4.3 節指標 | 如實回報 |
| V5 | **故障圍堵** | 第 3.5 節五種情境,各重複 10 次以上 | 飛行軟體 rate group 零 cycle slip;ML 自動恢復 |
| V6 | **對照組** | 同一份 F Prime(Linux 平台)在同一台 VM 的 Linux 上做 V5 | 呈現差異(預期 Linux 上 ML 失控會影響飛行軟體時序) |
| V7 | **時序量測** | F Prime ActiveRateGroup 遙測 + QNX tracelogger kernel trace【已查證:8.0 有 tracelogger / traceprinter / VS Code System Profiler】 | 數據附在 repo |

> **誠實揭露**:V5–V7 都在 QEMU/KVM 虛擬機裡量測,絕對數字受虛擬化影響。所以重點放在「同條件下 QNX vs Linux 的相對差異」和「有沒有 cycle slip」,Devpost 說明會明講這個限制。

### 7.2 建置步驟

|---|---|---|

### 7.3 資源分配(7.9 GB 的限制)
- WSL2 上限約 5 GB(`.wslconfig` 的 `memory=`)
- QNX 客體 1.5–2 GB、2 vCPU(精簡映像、無圖形介面)
- GDS 用 Windows 的瀏覽器看(WSL 轉發 localhost)
- 編譯時關掉 QEMU,避免記憶體不足

### 7.4 如果巢狀 KVM 開不起來
- QEMU 退回軟體模擬(TCG):**功能驗證不受影響**(V1–V4),但 **V5–V7 的時序數據會失真**
- 到時候需要你決定:① 接受只做功能 demo + 相對比較;② 改用一台 Raspberry Pi 5 做時序實驗;③ 換一台 16 GB 筆電(使用者 11/13 表示可設法取得)
- **這是第一週的關卡**,E2 失敗時會帶證據回來跟你討論,不會自己砍範圍
