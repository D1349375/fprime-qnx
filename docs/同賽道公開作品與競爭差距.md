# QNX Global Hackathon 同賽道公開作品與競爭差距

> 調研日期 2026-11-18。範圍為 Open-Source Contribution & Ports，評估 F Prime on QNX 爭取組別首獎所需的交付與證據，撇除本案實作進度。規劃細節見[競賽規劃缺口與驗收方案](競賽規劃缺口與驗收方案.md)。

**F Prime on QNX 有條件爭取組別首獎。** 第一項交付是既有 F Prime deployment 可採用的 QNX 平台。第二項是用同一平台交付可重跑的故障任務，量到飛行輸出是否準時、傳統 FDIR 何時接手，以及新顧問何時交回第一筆有效結果。同組公開作品已把乾淨建置、目標端驗證和機制對照做成評審可查的成果。本案有機會把這些做法串成一條完整的任務證據。

截至調研日，官方作品集尚未公開。本文列出五個在公開 repo 或送件文件自報同賽道的作品，核對其固定版本文件、測試腳本、可取得的原始結果與上游 PR。實測數字來自作者公開紀錄。這個樣本可供交付規劃與評審證據比較，完整參賽名單及名次仍無從確認。官方四項評分等權，同分時先比技術實作。 [官方作品集](https://qnx.devpost.com/project-gallery) · [官方規則 §4、§6、§8](https://qnx.devpost.com/rules)

## 五個公開案例

### PX4 on QNX

**最接近的飛控移植。** 作者的送件清單勾選已送出，並列明 Ports 類別。移植固定在 PX4 v1.17.0，目標是 QNX SDP 8.0.5、QEMU x86_64/KVM。乾淨 clone 腳本串起取用上游、套用變更、建置映像、部署與七項驗收，涵蓋優先權、時鐘、參數、故障圍堵及 MAVSDK 的完整模擬飛行。上游 PX4 PR #29765 截至調研日仍開啟。 [送件紀錄](https://github.com/Sarcastic-Soul/px4-qnx/blob/545adfe2f02f410f37f99fbb7a6cc5ef2623bde9/docs/submission.md) · [乾淨重跑腳本](https://github.com/Sarcastic-Soul/px4-qnx/blob/545adfe2f02f410f37f99fbb7a6cc5ef2623bde9/scripts/fresh-clone-test.sh) · [上游 PR #29765](https://github.com/PX4/PX4-Autopilot/pull/29765)

時序表中的 800 Hz 是 PX4 的目標更新頻率，指標包含更新數與相鄰更新間最長間隔。Linux 對照以一般使用者執行，無法取得其請求的即時優先權。作者也公開更高優先權負載壓住部分非控制工作與 EKF 的情況。故障場景驗證了背景程序崩潰期間 PX4 能完成模擬任務，logger 由腳本另行停啟。 [固定版本實驗結果](https://github.com/Sarcastic-Soul/px4-qnx/blob/545adfe2f02f410f37f99fbb7a6cc5ef2623bde9/docs/results.md)

**F Prime 差距。** 借鑑整個任務的驗收方式。從乾淨環境跑到 GDS 指令／事件往返，故障期間量到飛行元件實際提交的結果、時限與 FDIR 狀態，再追到顧問恢復有效服務。週期與負載依本案模擬場景訂定。

### rmw_qnx

**最直接的機制對照。** README 自報 Ports，標準 ROS 2 應用可透過 `RMW_IMPLEMENTATION` 選擇 middleware。作者在同一 QNX guest 用相同程式比較 Fast DDS、Cyclone DDS 和 `rmw_qnx`，並公開負載、優先權、CPU 配置、期限、重現命令與 kernel trace。指定負載下，兩套 DDS 每輪各有 40/200 次錯過 5 ms 期限。`rmw_qnx` 在報告主實驗的三輪均為 0/200。 [固定版本 README](https://github.com/Marc-Dvci/rmw_qnx/blob/088acd9d6fefb4770afd65a43bd28a7cfa251e38/README.md) · [實驗與各輪輸出](https://github.com/Marc-Dvci/rmw_qnx/blob/088acd9d6fefb4770afd65a43bd28a7cfa251e38/docs/RESULTS.md) · [原始紀錄](https://github.com/Marc-Dvci/rmw_qnx/blob/088acd9d6fefb4770afd65a43bd28a7cfa251e38/results/inversion-ros2-20261107-080444.txt)

同份報告列出未加負載時一次 `rmw_qnx` 逾期，以及歷次加載紀錄合計 3/3,000 次逾期。上游相容性測試另列未通過或未完成的項目。這些資料讓評審能分辨特定優先權反轉案例的改進、長尾與整體支援範圍。 [完整結果](https://github.com/Marc-Dvci/rmw_qnx/blob/088acd9d6fefb4770afd65a43bd28a7cfa251e38/docs/RESULTS.md)

**F Prime 差距。** 預先指定一個能歸因的對照，保持 guest、應用、故障、負載、回退規則與觀察時窗一致。優先考慮比較顧問崩潰後，SLM 是否啟用自動重啟對服務恢復的影響，同時公布兩組飛行任務的逾期數和分母。必要時再加 CPU 預算的機制測試。公開 OS 評估與追蹤材料的範圍依專案適用授權確認。 [QNX SLM 文件](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html) · [QNX 非商用授權 §4.6](https://www.qnx.com/download/download/51624/BB_QNX_Development_License_Non-Commercial_License_Class_v7_2025-12-10.pdf#page=6)

### Éclat

**最直接的故障圍堵競爭。** README 自報 Ports。作品以 WAMR 執行受限模組，公開 QNX 目標端拒絕未授權通道、終止 CPU 忙迴圈，以及控制迴圈在終止前、期間與後持續執行的紀錄。權限反例有一個確實在監聽的見證服務，能分辨政策拒絕與服務不存在。其證據索引為各個主張附上指令、日期、原始輸出及驗收結果。 [固定版本 README](https://github.com/Tradoooo/eclat/blob/9cd00c175893a47cf8cba0461f58c9bb8c04c1e3/README.md) · [證據索引](https://github.com/Tradoooo/eclat/blob/9cd00c175893a47cf8cba0461f58c9bb8c04c1e3/docs/preuves/INDEX.md) · [權限驗證紀錄](https://github.com/Tradoooo/eclat/blob/9cd00c175893a47cf8cba0461f58c9bb8c04c1e3/docs/preuves/qnx800/2026-11-14-secpol-ecl14.txt)

1 kHz 是案例的名目週期。目標端原始紀錄列出超過 1.5 ms 的間隔，作者將該 QEMU/KVM 場景的結論限定為迴圈持續運作。執行環境、名目週期、完成時限與實際結果是四項不同資訊。 [三階段迴圈紀錄](https://github.com/Tradoooo/eclat/blob/9cd00c175893a47cf8cba0461f58c9bb8c04c1e3/docs/preuves/qnx800/2026-11-12-boucle-1khz.txt)

**F Prime 差距。** 除了持續運作，驗收每個預定週期的任務輸出、回退結果和舊建議的拒絕原因。用同一條時間線呈現故障觸發、備援生效和新工作階段的第一筆有效推論結果。WebAssembly 沙箱與通用能力管理屬於 Éclat 的應用需求。

### zenoh-pico for QNX 8.0

**可獨立採用的移植。** README 自報 Ports。作者將 QNX 層做成上游支援的外部 CMake 平台套件，固定 zenoh-pico 1.10.2，附小型上游差異、工具鏈及下游匯入範例。作者在 x86_64 QNX/QEMU 記錄了 41/41 通過，含 40 個上游測試與一個移植測試。另外公開 QNX、Rust router 與 Linux 的雙向互通結果。aarch64le 標示到建置階段。 [固定版本 README](https://github.com/emilhuseyn/qnx-zenoh-pico/blob/f684296de74b7fe577271f79304d94ef0311162f/README.md) · [測試結果](https://github.com/emilhuseyn/qnx-zenoh-pico/blob/f684296de74b7fe577271f79304d94ef0311162f/test/results-x86_64.md) · [互通紀錄](https://github.com/emilhuseyn/qnx-zenoh-pico/blob/f684296de74b7fe577271f79304d94ef0311162f/test/interop-x86_64.md)

**F Prime 差距。** 以既有 deployment 當平台庫的下游使用者。列清楚哪些問題由平台解決、哪些配置由使用者調整，以及 QEMU x86_64 上哪些必要 OSAL 與整合測試確實執行。每個目標架構的建置與執行證據各有狀態即可。

### open62541 on QNX 8.0

**上游差異小、審查範圍明確。** 此處比較 `buahrasa01-hub` 的 v1.5.1 案例，README 明列 Ports。作者將 QNX 建置阻礙逐一對到標頭、事件迴圈及系統連結差異，提供 QEMU 目標端的 round-trip 測試和主機 client 操作情境，另有獨立加密測試。需要 `libcheck` 的上游 suite 未在目標端執行，README 有說明。PR #8717 截至調研日仍開啟，範圍為已存在於主線的相近修正回移至 1.5 維護分支。 [固定版本 README](https://github.com/buahrasa01-hub/open62541-qnx/blob/c0934086952294d08e930db08fffe61a8a8f4895/README.md) · [上游 PR #8717](https://github.com/open62541/open62541/pull/8717)

**F Prime 差距。** 將 QNX CMake、工具鏈、OSAL 和必要的拓撲接線分成可審閱的變更，每部分說明原行為、QNX 差異和回歸證據。上游 issue 或 PR 可以承載這份審查材料，開啟或合併狀態照實標示。 [F Prime 平台貢獻指引](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/#how-to-contribute-a-new-supported-platform)

## 首獎交付的優先順序

| 優先 | 交付 | 評審可查驗的證據 |
| --- | --- | --- |
| 1 | **既有 deployment 的採用驗收** | 固定上游版本。從乾淨環境接起不含 ML 的既有 deployment，列出 timer、平台與建置設定的必要差異。保留原任務元件，附 GDS 指令／事件往返及必要 OSAL 目標端結果。 |
| 2 | **同一任務的故障全程** | 以事先宣告的任務週期和期限，逐輪發布完成、逾期、漏期與樣本數。並排標記顧問不回覆或崩潰、備援接手、舊建議被拒、以及新工作階段第一筆有效結果。健康遙測下的「無異常」也是有效結果。 |
| 3 | **一項同環境的機制對照** | 同 QNX、同腳本、同一個故障場景，只切換待驗證的機制。結果接近時，保留兩組數字及觀察範圍，將主張放在實測成立的應用行為。 |
| 4 | **送件首頁的證據索引** | 以同一個送件 commit 或 tag，將主張連到重現命令、原始結果、必要限制和影片時間碼。影片先呈現任務結果，再解釋使用的 QNX 機制。 |

主線維持 QEMU x86_64、可匯入的平台庫、一個有已知故障來源的模擬任務，以及一個可替換的 ML 顧問介面。各競品的迴圈頻率、測試數量、額外架構、通訊中介軟體與介面規模服務於各自的產品。F Prime 的額外功能可依完成上述驗收的需要排序。 [規劃與驗收細節](競賽規劃缺口與驗收方案.md)
