# F Prime on QNX 得名規劃與驗收方案

> 2026-11-18｜規劃評估與調研，撇除實作進度。對應[專案規劃書](專案規劃書.md)第 3、4、6、8、9 節。下列驗收條件是設計建議，量測數字須由實驗產出。

## 得名定位

**保留題目，以 Open-Source Contribution & Ports 組別亞軍為具體目標。** 能重現飛行任務在 ML 故障下的時序與回退行為，就有理由競逐組別首獎及 Best Use of QNX-specific Technologies。官網作品集尚未公開，現階段可判斷題目與評分契合度。技術實作、設計、潛在影響、創新與 AI 創意四項等權。 [官方規則 §6、§8](https://qnx.devpost.com/rules) · [官方作品集](https://qnx.devpost.com/project-gallery)

**參賽主張**　讓既有 F Prime 開發者把飛行軟體移植到 QNX 8.0，並用同一套參考部署驗證這件事：在指定的模擬任務與負載下，ML 推論卡死或崩潰時，飛行任務仍能依截止時間運作，傳統故障處置可接手，ML 重啟後經驗證才重新提供建議。

F Prime 的官方支援及規劃平台未列 QNX，移植有清楚的採用對象。F Prime 與 mlpack 已有機上異常偵測先例，NASA Goddard 的另一套飛行框架 cFS 也已支援 QNX 8.0。本作的差異集中在**供 F Prime 團隊採用的 QNX 平台庫，以及可重現的 ML 故障圍堵證據**。 [F Prime 支援平台](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/) · [SmallSat 的 F Prime／mlpack 實作](https://digitalcommons.usu.edu/smallsat/2026/all2026/66/) · [NASA cFS 公告](https://etd.gsfc.nasa.gov/capabilities/core-flight-system/news/nasas-cfs-expands-operating-system-support-with-addition-of-qnx/)

| 2 | 雙行程已規劃，飛行任務的通訊與回退邊界仍需明定 | IPC 執行緒邊界、顧問狀態與故障注入驗收表 |

## 1. 定義飛行任務時序與實驗對照

### 時序契約

先選一個能對應任務結果的工作，例如 ADCS 模擬的一次「讀取感測器、更新太陽向量估計、提交有效性狀態」。完成點設在結果已提交給下一階段處置之時。用同一個 guest 的單調時鐘記錄事件；以 `CLOCK_MONOTONIC` 為預設。F Prime 的 `cycle slip` 保留作輔助指標，非同步子元件的完成時間須另量。 [QNX 單調時鐘](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.prog/topic/timing_Time_functions.html) · [F Prime Rate Groups and Timeliness](https://fprime.jpl.nasa.gov/latest/docs/user-manual/design-patterns/rate-group/)

| 欄位 | 定義與驗收 |
| --- | --- |
| `T`、`D` | `T` 是任務週期，`D` 是自預定釋放到完成的截止時間。可用 `T = D = 20 ms` 作為試跑起點。定稿值須說明如何配合所選模擬任務與負載，並於正式測試前凍結。 |
| `release_k`、`start_k`、`finish_k` | `release_k = t0 + k × T`，後兩欄記錄真正開始、結果提交的時刻。各週期帶序號，即使排程跳過一個週期也能從預期序號計入。 |
| 延遲與逾期 | 報告 `start_k − release_k` 與 `finish_k − release_k` 的 p50、p99、觀察最大值；並列逾期數／全部應執行週期數。完成時間超過 `release_k + D` 或該週期未完成，均算逾期。無完成時間的週期單列。 |
| `T_fallback`、`T_rejoin` | 分別記錄從故障發生到回退生效、到新工作階段的首筆合格建議被接受的時間。另記錄故障判定與新行程啟動的時間，以區分偵測、重啟和暖機。正式測試前依 TTL、監看與 SLM 設定訂出各自接受值。 |
| 主驗收 | 完整配置在預先宣告的名目負載和必要故障測試下達到零觀察逾期，且符合回退、恢復與拒絕舊建議的條件。公開量測結論限定在報告列出的映像、資源、工作負載和樣本數。 |

### 對照組與採樣

| 組別 | 固定條件與實驗目的 |
| --- | --- |
| Q0 · QNX + 傳統 FDIR | 保留相同飛行工作與輸出，關閉 ML，取得時序基準。 |
| Q1 · QNX + 完整配置 | 雙行程、非阻塞交接、正式排程及監看全部啟用。包含名目、背景負載、故障、回退與重連。 |
| Q2 · QNX + 停用一項資源機制 | 首先比較 ML 推論執行緒的 `SCHED_SPORADIC` 與相同正常優先權的無預算配置。維持雙行程、同一 ML 工作與監看規則，記錄預算耗盡後的有效優先權、同核心競爭和時序。若監看太快終止而遮蔽排程差異，增加一組限定時窗的獨立量測，明記該組設定。 |
| Q3 · QNX + 暫停卡死後的自動恢復 | 選做。兩組保留相同的過期回退，觀察 SLM 與監看能縮短多少顧問不可用時間。把回退時間和重返可用時間各自報告。 |
| L1 · 等價 Linux 參考 | 選做。使用同版 F Prime、同負載、雙行程和功能等價的回退；固定 guest vCPU/RAM、CPU 親和性、模型及模型執行緒數。公開使用的 Linux 核心和排程配置，記錄 PREEMPT_RT 及即時優先權的實際狀態。結論歸於兩種配置。 [Linux PREEMPT_RT](https://docs.kernel.org/core-api/real-time/theory.html) |

- 正式組別共享可版本化的故障劇本、負載與種子；交錯執行不同組別。每個必要故障可沿用至少 10 次重複的規劃，固定暖機、故障時窗和觀察終點，記錄每次完整週期數及主機負載。另做較長的名目與負載測試，避免只評估單次短 Demo。
- 報告 VM、QEMU 加速模式、vCPU、記憶體、主客體版本、工作與追蹤設定。同機對照可以控制部分條件，仍需保留 VM 外部排程造成的變異。
- 原始記錄至少含 `run_id`、配置、`cycle_id`、三個時間戳、故障標記、顧問狀態、佇列溢出與處置結果。飛行迴圈將固定大小記錄寫入預配置緩衝區，由旁路匯出，記錄遺失筆數。以短時段 QNX kernel trace 解釋一次 IPC 或排程事件，正式統計的追蹤設定保持一致。
- 圖表保留截止線、故障及回退標記，並列原始樣本總數。若 Q1、Q2 都準時，仍可如實顯示 CPU 正常優先權時段、資源競爭及顧問恢復差異。公開 QNX 與 Linux 的效能比較前處理第 4 節的授權確認。

## 2. 把故障隔離寫成可驗收的架構條件

### 通訊與權限

- **飛行工作只做有界交接。** 在 `FlightSW` 保留獨立 IPC 執行緒與預配置、固定容量的資料交接區。飛行迴圈發布最新遙測快照、讀取合格建議，每個週期處理固定上限的輸入，避免等待回覆、配置記憶體、檔案 I/O 及需要 IPC worker 釋放的鎖。將交接邊界放在 `GenericHub` 呼叫之前，因為它在呼叫 driver 前已取用緩衝區並序列化。F Prime v4.4.2 的預設 `PriorityQueue` 在 `NONBLOCKING` 路徑仍取 mutex。可驗證該版無鎖佇列在目標平台上的行為，或使用固定長度、單生產者／單消費者且失敗即返回的交接區。滿載時明定捨棄策略及 drop counter，並驗收程序不會因佇列滿而 assertion。 [GenericHub v4.4.2](https://github.com/nasa/fprime/blob/v4.4.2/Svc/GenericHub/GenericHub.cpp#L31-L47) · [預設佇列](https://github.com/nasa/fprime/blob/v4.4.2/Os/Generic/PriorityQueue.cpp#L187-L205) · [無鎖佇列](https://github.com/nasa/fprime/blob/v4.4.2/Os/Generic/LocklessPriorityQueue.cpp)
- **沿用 FlightSW 為 server 的拓撲。** `MlAdvisor` 以固定上限的頻率請求新快照或送交建議。FlightSW 的 IPC worker 讀取快照、快回覆並交接合格封包，推論在 ML 執行緒執行。若沿用 `GenericHub`，將封包限制為遙測與具型別的建議，在進入解碼前驗證版本、類型、索引與長度，指令分派器維持獨立。`GenericHub` 規格允許丟棄傳輸錯誤的訊息，應由傳輸層另外匯報丟棄、逾時和重連狀態。 [F Prime GenericHub 設計](https://fprime.jpl.nasa.gov/v4.4.0/Svc/GenericHub/docs/sdd/) · [v4.4.2 接收路徑](https://github.com/nasa/fprime/blob/v4.4.2/Svc/GenericHub/GenericHub.cpp#L104-L145)
- **訊息期限需要驗證兩種阻塞。** `TimerTimeout` 可處理 SEND 與 REPLY 階段，但 `name_attach(NULL, …)` 建立的通道帶 `_NTO_CHF_UNBLOCK`，收件後逾時可能只向 server 送 unblock pulse，仍需要 server 回覆或回錯。現有路徑應正確處理 pulse，並以獨立的顧問過期判斷保護飛行迴圈。若另要求 IPC 呼叫本身有明確返回上限，再評估自建通道、明定 flags，實測收件前與收件後的卡死。 [QNX `name_attach`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/n/name_attach.html) · [QNX `TimerTimeout`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/t/timertimeout.html)
- **限制連線與實際優先權。** 對 bridge 通道指派專用 security type，依實際註冊路徑配置政策，允許必要服務與 bridge 連線。驗收允許的連線和應拒絕的正式指令通道。QNX 訊息傳遞預設會改變收件執行緒的有效優先權，需以 trace 驗證 IPC worker 的實際優先權；有必要時才為自建通道考慮固定優先權。 [QNX security policy 語言](https://qnx.com/developers/docs/8.0/com.qnx.doc.security.system/topic/manual/secpol_language.html) · [QNX 訊息優先權繼承](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.sys_arch/topic/ipc_Priority_inheritance_messages.html)

### 顧問生命週期與資源監看

1. **可用。** 建議附 FlightSW 發給該連線的工作階段識別、來源快照序號、動作與理由。FlightSW 依自身記錄的快照取樣時間判斷新鮮度，拒絕跨工作階段、過期、重複、未發出序號、格式錯誤及狀態不符的動作。重複封包不重複執行動作。
2. **不可用。** 崩潰、斷線或最後一次有效推論進展超過期限時，Gate 撤銷該工作階段並啟用原本的 FDIR。行程存活或 IPC heartbeat 可作診斷；推論進展須有可驗證的新序號與完成事件。單調時鐘的監看要能察覺睡眠、鎖等待及收件後停住。
3. **重新加入。** 監看偵測活著但卡死時，依策略觸發顧問異常終止，由 SLM 按重啟設定處理；實測該終止原因是否觸發 `repair=restart`。SLM 相依性只由顧問指向飛行服務，避免重啟顧問時重啟飛行服務。新連線獲新識別，完成載入、暖機與新鮮結果檢查後才可提建議。反覆故障時維持回退並套用重啟限速。 [QNX SLM](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)

`SCHED_SPORADIC` 的預算屬於**執行緒在正常優先權下的執行時間**，耗盡後可在較低優先權執行。把推論、OpenBLAS 與 IPC 的執行緒數和有效排程納入清單，優先使用容易列舉的單執行緒推論配置。CPU-time 計時器可偵測忙迴圈消耗，等待中的故障由經過時間監看偵測。QNX 8.0 也有 `RLIMIT_AS` 及 SLM `rlimit` 文件，原規劃的待查事項可更新為驗證目標映像的**虛擬位址空間**限制與配置失敗路徑，另記錄實體記憶體觀察。 [QNX Sporadic scheduling](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.sys_arch/topic/kernel_Sporadic_scheduling.html) · [QNX 執行時間監看](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.prog/topic/timing_execution_times.html) · [QNX `setrlimit`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/s/setrlimit.html) · [QNX SLM](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)

| 故障注入 | 判定條件 |
| --- | --- |
| ML 忙迴圈、同核心 CPU 競爭 | 量到飛行任務時序、ML 預算耗盡後的優先權、回退及重啟；飛行工作符合第 1 節主驗收。 |
| ML 不再請求或只回 heartbeat | 過期後維持 FDIR；記錄推論進展監看觸發與重新加入。 |
| IPC 收件前停住、收件後不回覆 | 用 IPC 測試組件分別覆蓋兩個階段，量到通訊端狀態；飛行迴圈均能按時執行，Gate 在有效期後停止採用建議。 |
| ML 程序退出後重新加入 | 觀察 SLM 啟動新程序、完成暖機；舊工作階段的建議被拒，新鮮建議符合條件才受理。 |
| 佇列滿載、重複或過期建議 | 飛行迴圈的每週期工作量維持上限；記錄丟棄與拒絕原因；同一動作沒有重複生效。 |
| 目標映像上的記憶體上限或連線權限 | 針對啟用的機制，分別記錄超限配置的處置和經授權／未授權通道的結果。 |

## 3. 驗證 ML 的價值與恢復行為

### 實驗 A · 真實資料的片段偵測

使用 OPSSAT-AD **v2**，固定 DOI `10.5281/zenodo.15108715`、資料檔雜湊及取用方式。v2 隨附 MIT 資料授權，引用資料時保留作者與授權資訊。資料包含取自九個通道的 2,123 個人工切段，每段是單通道時序，提供正常／異常標籤和手工特徵。用 `dataset.csv` 的 `anomaly` 和 `train` 欄位重現切分。論文的訓練總數有誤植，依表 1 各類小計預期訓練 1,594、測試 529，下載後從固定版本 CSV 逐欄重算。 [OPSSAT-AD v2 資料](https://zenodo.org/records/15108715) · [資料授權檔](https://zenodo.org/records/15108715/files/LICENSE?download=1) · [資料論文表 1](https://arxiv.org/html/2407.04730v1#S2)

從訓練集劃分驗證資料，所有參數、正規化及閾值在訓練／驗證上定稿。固定測試集回報 AP、precision、recall、MCC 和主機／QNX 一致性。若與論文的 `AUC_PR` 數字比較，採作者範例中的 `average_precision_score` 定義。圖表標明「專家切段的異常分類」。 [作者的重現程式](https://github.com/kplabs-pl/OPS-SAT-AD/blob/main/modeling_examples.ipynb)

專家切段的長度、缺口與邊界會影響特徵。線上推論另外固定樣本時間尺度、因果視窗 `[t−W, t]`、步距、暖機、缺值與資料過期規則。訓練與評估使用相同前處理；缺樣分開記錄，視窗未達最低有效樣本時輸出「資料不足」。閉迴路測試的模型與門檻使用獨立模擬訓練／驗證劇本，不假定真實切段上訓練的模型可直接轉移到模擬。若希望測試轉移效果，另列模型與前處理設定。 [OPSSAT-AD 方法與特徵](https://arxiv.org/html/2407.04730v1#S2)

### 實驗 B · 同一姿態感測情境的線上偵測與處置

**建議情境**　模擬其中一顆粗略太陽感測器（光電二極體）逐步偏移，使太陽向量估計劣化。每顆感測器由照入角、可視範圍、遮蔽與雜訊生成讀值。配置有重疊視野的感測器；從估計中去掉一顆前，檢查剩餘受光通道的幾何條件足以估計太陽向量，再用獨立的感測器一致性條件判定是否接受該動作。模擬器的真值由評估腳本使用，與 Gate 的輸入隔離。挑戰用語聚焦在**太陽向量估計恢復**，與感測器模型的能力一致。 [Basilisk 粗略太陽感測器模型](https://avslab.github.io/basilisk/Documentation/simulation/sensors/coarseSunSensor/coarseSunSensor.html) · [NASA SmallSat GNC](https://www.nasa.gov/smallsat-institute/sst-soa/guidance-navigation-and-control/)

| 比較組 | 運作方式 |
| --- | --- |
| 傳統 FDIR | 使用具持續性判斷的殘差或趨勢門檻，經相同的處置 Gate 和估計器。用模擬驗證組選參數，使兩種偵測器適用同一誤報事件上限。 |
| ML + Gate | 用一個模型處理因果視窗。ML 提出單通道隔離建議；Gate 檢查新鮮度、獨立一致性、可觀測性、狀態及限頻後才核准。 |
| ML 故障後回退 | 用相同感測器故障與負載，在預定時刻讓 ML 不回覆或退出；觀察獨立 FDIR 和太陽向量估計繼續運作。 |

在正式測試前凍結故障起點與斜率、種子、誤報事件的分組方式、可接受的太陽向量角誤差、連續達標週期數及可比較的時間窗。至少納入正常姿態變化、短暫遮蔽或進入陰影，以及排除後受光幾何不足等反例。未知異常可先通知並啟用 FDIR。估計持續無效時，依獨立條件進入模擬的**子系統降級狀態**，加入維持時間與狀態控制，避免誤報造成反覆切換。ECSS 將整星安全模式的進入條件連到系統層級的關鍵功能，並將退出交由地面控制，建議據此調整原案「未知異常 → safe mode」的對應表。 [ECSS-E-ST-70-11C Rev.1 §5.7.5.6](https://ecss.nl/wp-content/uploads/2025/10/ECSS-E-ST-70-11C-Rev.1-%2815October2025%29.pdf)

以時間軸分別記錄**故障起點、首次有效警報、Gate 核准、處置生效及穩定恢復**。保留感測器的偏移輸出，處置只移除該讀值。以估計與模擬真值的角誤差判斷是否連續數個週期回到容許範圍。報告漏報數、正常劇本的誤報事件率、正確／不必要／錯誤處置數、處置前後角誤差及恢復時間。將漏報與無法恢復的劇本明列，標記各延遲統計的有效樣本數。如果只有警報提早，結論聚焦於預警價值。恢復改善以處置與角誤差結果判定。

## 4. 讓移植能被採用，並讓評審能核對

**首位採用者**　已有 F Prime deployment、想把應用移到 QNX 並評估 ML 故障隔離的飛行軟體整合者。平台庫與 ADCS 參考部署維持清楚介面，驗收包括不含 ML 的標準 `Ref` 或小型等效參考部署。F Prime 官方平台貢獻流程需要平台庫、參考專案、文件與持續測試及維護規劃；核心改動先依上游流程開 issue，PR 狀態依實際進度標示。 [F Prime 平台貢獻指引](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/#how-to-contribute-a-new-supported-platform) · [上游貢獻流程](https://fprime.jpl.nasa.gov/latest/CONTRIBUTING/#code-contribution-process)

1. **固定版本。** 首要目標為規劃中的 QNX SDP 8.0.5、QEMU x86_64、qcc 和固定的 F Prime commit。依賴、建置選項及 SDK 套件來源可重建。逐一標示其他架構的驗證狀態；CPU 或記憶體介面如有缺項，附支援範圍、測試結果和影響。
2. **乾淨環境驗收。** 另一位開發者備妥自己的 SDK 與目標映像後，從提交用版本依文件建置，跑目標端的必要 OSAL 測試，在 GDS 發送 `CMD_NO_OP` 並看到預期事件，然後重現一次 ML 卡死、飛行任務仍執行的測試。記錄指令、預期輸出、執行結果與障礙，修正文件後重跑。 [F Prime v4.4.2 指令整合測試](https://github.com/nasa/fprime/blob/v4.4.2/Svc/CmdDispatcher/test/int/test_cmd_dispatcher.py) · [QNX 官方 QEMU 建置教學](https://qnx.github.io/codelabs/setup-qsti-qemu-on-ubuntu/index.html)
3. **QNX Evidence Index。** 每項主張對應送件 commit 的檔案或函式、可辨識的 QNX 版本／目標／工具鏈、目標端輸出或 trace、影片時間碼。Devpost 需有公開開源 repo、上游 URL、已有 PR 的連結、英文材料或翻譯與公開的三分鐘內目標端 Demo。QEMU 符合規則。評審可以只看書面、圖與影片，故每個主張要能從送件材料本身核對。 [官方規則 §4、§6](https://qnx.devpost.com/rules)
