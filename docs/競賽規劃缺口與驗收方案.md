# F Prime on QNX 得名規劃與驗收方案

> 2026-11-18｜同賽道比對與獨立審查後修訂。對應[專案規劃書](專案規劃書.md)第 3、4、6、8、9 節。本文定義建議的驗收與量測方式。公開作品、比較證據和範圍取捨見[同賽道公開作品與競爭差距](同賽道公開作品與競爭差距.md)。

## 得名定位

**以 Open-Source Contribution & Ports 組別首獎為目標。** 同一個公開版本須同時交付可採用的 F Prime 移植，以及可重現的任務故障實驗。Best Use of QNX-specific Technologies 可沿用核心實驗的證據。官網作品集尚未公開，首獎是規劃目標。技術實作、設計、潛在影響、創新與 AI 創意四項等權。 [官方規則 §6、§8](https://qnx.devpost.com/rules) · [官方作品集](https://qnx.devpost.com/project-gallery)

**參賽主張**　既有 F Prime 開發者能用平台庫將 deployment 移植到 QNX 8.0。同一平台庫的 ADCS 參考部署可重現顧問失聯、飛行工作依指定期限提交可驗證的估計結果或降級狀態、傳統故障處置接手，以及顧問重啟後憑新鮮有效推論重新加入。

F Prime 的官方支援及規劃平台未列 QNX，移植有清楚的採用對象。F Prime 與 mlpack 已有機上異常偵測先例，NASA Goddard 的另一套飛行框架 cFS 也已支援 QNX 8.0。本作的差異集中在**供 F Prime 團隊採用的 QNX 平台庫，以及可重現的 ML 故障圍堵證據**。 [F Prime 支援平台](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/) · [SmallSat 的 F Prime／mlpack 實作](https://digitalcommons.usu.edu/smallsat/2026/all2026/66/) · [NASA cFS 公告](https://etd.gsfc.nasa.gov/capabilities/core-flight-system/news/nasas-cfs-expands-operating-system-support-with-addition-of-qnx/)

| 優先順序 | 首獎驗收 | 評審可查驗的成果 |
| --- | --- | --- |
| 1 | 另一個 deployment 可以採用 QNX 平台庫 | 固定版本的乾淨重建、原任務元件、移植差異、目標端 OSAL 與 GDS 結果 |
| 2 | ML 失效時飛行工作會依時限提交結果，回退與重新加入可以重現 | 時序契約、同一事件的輸出時間軸、SLM 單項對照、原始資料與每輪分母 |
| 3 | 有用的警報可以被轉成正確處置，無效建議可被拒絕 | 真實片段推論結果、模擬的警報與恢復指標、Gate 正反例 |

## 1. 驗收既有 F Prime deployment 的移植

**首位採用者**　已有 F Prime deployment、想在 QNX 上跑既有應用並評估 ML 隔離的飛行軟體整合者。固定 F Prime `v4.4.2` 對應 commit、QNX SDP 8.0.5、QEMU x86_64、qcc 與依賴，再用同一套公開版本完成兩段驗收。上游平台貢獻流程也以平台庫、參考專案、文件、持續測試及維護規劃為基礎。 [F Prime 平台貢獻指引](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/#how-to-contribute-a-new-supported-platform)

1. **獨立部署。** 以 F Prime `Ref` 作為首選採用案例。v4.4.2 的 `Ref` 把 `Svc.LinuxTimer` 接到 rate group driver，上游只為 Linux 和 Darwin 註冊該元件。列出平台註冊、工具鏈、timer 與拓撲接線等必要差異，保留原任務元件，並標明需要調整的 `Ref` 功能與測試。若採另一個既有、與本案 ADCS／ML 無關的 deployment，明列其來源、替換原因和已驗證範圍。用可審閱的設定與差異說明如何匯入平台庫。 [Ref timer 接線](https://github.com/nasa/fprime/blob/v4.4.2/TestDeploymentsProject/Ref/Top/topology.fpp#L81-L82) · [LinuxTimer 建置限制](https://github.com/nasa/fprime/blob/v4.4.2/Svc/LinuxTimer/CMakeLists.txt)
2. **目標端證據。** 從乾淨目錄依文件建置，記錄 QNX 版本及工具鏈，執行目標端的 OSAL 測試，透過 GDS 發送 `CMD_NO_OP` 並核對預期事件，再核對一項週期遙測或任務輸出。報告把通過、失敗、跳過及不支援分別列出，列明 OSAL 支援範圍和未支援功能的行為。另一位開發者可使用自己的 SDK 重跑。最低驗收是獨立的乾淨環境重建。 [F Prime v4.4.2 指令整合測試](https://github.com/nasa/fprime/blob/v4.4.2/Svc/CmdDispatcher/test/int/test_cmd_dispatcher.py) · [QNX 官方 QEMU 建置教學](https://qnx.github.io/codelabs/setup-qsti-qemu-on-ubuntu/index.html)
3. **同版本的第二段驗收。** 用該平台庫建置 ADCS 參考部署並重現第 2、3 節的故障實驗。提供一個文件入口及可重跑腳本，分別輸出移植驗收、故障驗收和對應原始紀錄。可一般化的上游修正附最小變更、重現步驟與測試證據，依上游流程討論與投稿，據實標示狀態。 [F Prime 上游貢獻流程](https://fprime.jpl.nasa.gov/latest/CONTRIBUTING/#code-contribution-process)

## 2. 定義飛行任務時序與實驗對照

### 時序契約

先選一個能對應任務結果的工作，例如 ADCS 模擬的一次「讀取感測器、更新太陽向量估計、提交有效性狀態」。完成點設在結果已提交給下一階段處置之時。用同一個 guest 的 `CLOCK_MONOTONIC` 記錄事件。F Prime 的 `cycle slip` 是輔助指標，反映前一週期仍執行時又收到 `CycleIn`。遺漏的釋放及非同步子元件的完成時間需以排定週期和下游輸出另量。 [QNX 單調時鐘](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.prog/topic/timing_Time_functions.html) · [F Prime v4.4.2 ActiveRateGroup](https://github.com/nasa/fprime/blob/v4.4.2/Svc/ActiveRateGroup/ActiveRateGroup.cpp#L96-L118)

| 欄位 | 定義與驗收 |
| --- | --- |
| `T`、`D` | `T` 是任務週期，`D` 是自預定釋放到完成的截止時間。可用 `T = D = 20 ms` 作為試跑起點。定稿值須說明如何配合所選模擬任務與負載，並於正式測試前凍結。 |
| `release_k`、`start_k`、`finish_k` | `release_k = t0 + k × T`，後兩欄記錄真正開始、結果提交的時刻。各週期帶序號，即使排程跳過一個週期也能從預期序號計入。 |
| 延遲與逾期 | Record the release-to-start and release-to-commit distributions and the deadline margin in local evidence. Count uncompleted or late cycles as misses and use all scheduled cycles as the denominator. |
| `T_fallback`、`T_rejoin` | 以實際故障注入時間為起點。`T_fallback` 量到傳統 FDIR 的決策及可供下游使用的狀態首次提交。`T_rejoin` 量到新工作階段的首筆新鮮、合格推論結果，包含「沒有異常、無建議」。另記錄最後合格推論、故障判定、舊行程退出、新行程啟動與暖機完成。正式測試前分別定義接受時限。 |
| 主驗收 | Apply the configured deadline to each planned cycle. Check the expected valid output or degraded state, rejection of old advice, fallback and any expected rejoin. Record the observed results and the full test scope locally. See [the current timing contract](專案規劃書.md#62-時序契約). |

### 對照組與採樣

| 組別 | 固定條件與實驗目的 |
| --- | --- |
| Q0 · QNX + 傳統 FDIR | 保留相同飛行工作與輸出，關閉 ML，用來估算顧問配置帶來的額外工作量。 |
| Q1 · QNX + SLM `repair=restart` | 完整配置。正式驗收含健康、活著但停止產出有效推論、異常退出與重連。用異常退出情境與 Q2 做主對照。 |
| Q2 · QNX + SLM `repair=none` | 維持同版映像與執行檔、相同顧問輸入、負載、注入時機、期限及回退策略，只調整顧問的退出修復設定。兩組用同樣的異常退出腳本，停止手動或其他自動重啟路徑，從注入到首筆新鮮推論使用相同觀察窗。未重返的結果記為「觀察窗內未重返」。 [QNX SLM `repair`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html) |
| Q3 · QNX 排程機制驗證 | 選做。比較 `SCHED_SPORADIC` 與相同正常優先權的無預算配置。確認相關工作競爭同一 vCPU，且測試期間實際耗盡預算。若監看先終止顧問，可另做限定時窗的資源觀察。量有效優先權、正常優先權執行時間及其他任務受影響的程度，保留期限結果。 [QNX Sporadic scheduling](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.sys_arch/topic/kernel_Sporadic_scheduling.html) |
| L1 · 等價 Linux 參考 | 選做。使用同版 F Prime、同負載、雙行程和功能等價的回退。固定 guest vCPU/RAM、CPU 親和性、模型及模型執行緒數。公開使用的 Linux 核心和排程配置，記錄 PREEMPT_RT 及即時優先權的實際狀態。結論歸於兩種配置。 [Linux PREEMPT_RT](https://docs.kernel.org/core-api/real-time/theory.html) |

- 正式組別共享可版本化的故障劇本、負載與種子，交錯執行不同組別。試前固定暖機、故障位置、總觀察窗及每個情境的重複數。可沿用每個必要故障至少 10 次的規劃。正常實驗的每輪初始狀態應一致，並與故意連續故障、驗證 SLM 限速的測試分開。
- 報告 VM、QEMU 加速模式、vCPU、記憶體、主客體版本、工作與追蹤設定。同機對照可以控制部分條件，仍需保留 VM 外部排程造成的變異。
- Keep the configuration, fault identifier, run and cycle identifiers, timestamps, output states, process and advisor session identifiers, queue overflow and action results in local evidence. Mark runs with insufficient timing records as inconclusive, retain their evidence and repeat them. Include all measured guest delays in conclusive runs. Keep traces identified by capture configuration.
- Align deadlines, fault injection, fallback and rejoin on the local timeline. Retain per-run sample sizes, verdicts and the Q1/Q2 comparison. For Q3, record budget and scheduling observations alongside each deadline verdict. Apply the release scope in [the project plan](專案規劃書.md#94-授權與公開材料必做) to public demonstrations.

## 3. 把故障隔離寫成可驗收的架構條件

### 通訊與權限

- **飛行工作只做有界交接。** 在 `FlightSW` 保留獨立 IPC 執行緒與預配置、固定容量的資料交接區。飛行迴圈發布最新遙測快照、讀取合格建議，每個週期處理固定上限的輸入，避免等待回覆、配置記憶體、檔案 I/O 及需要 IPC worker 釋放的鎖。將交接邊界放在 `GenericHub` 呼叫之前，因為它在呼叫 driver 前已取用緩衝區並序列化。F Prime v4.4.2 的預設 `PriorityQueue` 在 `NONBLOCKING` 路徑仍取 mutex。可驗證該版無鎖佇列在目標平台上的行為，或使用固定長度、單生產者／單消費者且失敗即返回的交接區。滿載時明定捨棄策略及 drop counter，並驗收程序不會因佇列滿而 assertion。 [GenericHub v4.4.2](https://github.com/nasa/fprime/blob/v4.4.2/Svc/GenericHub/GenericHub.cpp#L31-L47) · [預設佇列](https://github.com/nasa/fprime/blob/v4.4.2/Os/Generic/PriorityQueue.cpp#L187-L205) · [無鎖佇列](https://github.com/nasa/fprime/blob/v4.4.2/Os/Generic/LocklessPriorityQueue.cpp)
- **沿用 FlightSW 為 server 的拓撲。** `MlAdvisor` 以固定上限的頻率請求新快照或送交推論結果。FlightSW 的 IPC worker 讀取快照、快回覆並交接合格封包，推論在 ML 執行緒執行。建議把介面收斂成「遙測快照」與「推論結果」兩種具型別的資料，指令分派器維持獨立。若沿用 `GenericHub`，在進入解碼前驗證版本、類型、索引與長度。由傳輸層匯報丟棄、逾時和重連狀態。若通用 Hub 難以維持窄介面，可評估用只接受這兩種資料的 QNX bridge。 [F Prime GenericHub 設計](https://fprime.jpl.nasa.gov/v4.4.0/Svc/GenericHub/docs/sdd/) · [v4.4.2 接收路徑](https://github.com/nasa/fprime/blob/v4.4.2/Svc/GenericHub/GenericHub.cpp#L104-L145)
- **分清顧問停止產出與 IPC server 不回覆。** 主要故障是 ML client 活著但停止產出，飛行迴圈以獨立的結果過期判斷切入回退。FlightSW 的 IPC worker 收件前停住或收件後不回覆，則歸為通訊元件測試。`TimerTimeout` 可涵蓋 SEND 與 REPLY 階段，但 `name_attach(NULL, …)` 建立的通道帶 `_NTO_CHF_UNBLOCK`，收件後可能仍需要 server 處理 unblock pulse 才能返回。若確有 IPC 呼叫本身須在時限內返回的需求，再評估自建通道與 flags。 [QNX `name_attach`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/n/name_attach.html) · [QNX `TimerTimeout`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/t/timertimeout.html)
- **核對實際權限與優先權。** QNX 訊息傳遞預設會影響收件執行緒的有效優先權，應確認 IPC worker 的實際排程與飛行迴圈優先關係。若主張 `secpol` 隔離，為 bridge 通道指派專用 security type，驗證允許的連線和對確實在聆聽的非授權端點的拒絕。安全主張限於已測的連線路徑與 Gate 行為。 [QNX security policy 語言](https://qnx.com/developers/docs/8.0/com.qnx.doc.security.system/topic/manual/secpol_language.html) · [QNX 訊息優先權繼承](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.sys_arch/topic/ipc_Priority_inheritance_messages.html)

### 顧問生命週期與資源監看

1. **可用。** 每次完成推論回報 FlightSW 發給該連線的工作階段識別、來源快照序號及結果類型。有效結果包含「無異常、無動作」或一筆含目標與理由的建議。FlightSW 以自身記錄的快照取樣時間驗證新鮮度，拒絕跨工作階段、過期、重複、未發出序號或格式錯誤的封包，建議動作再交 Gate 檢查狀態與適用性。
2. **不可用。** 崩潰、斷線或應有的推論進度超過期限時，Gate 撤銷該工作階段並啟用傳統 FDIR。依實際取樣、視窗步距和暖機設定有效結果的期限，避免把預期等待或沒有異常誤判為卡死。由飛行應用的單調時鐘及新快照序號判定進度，heartbeat 可另作診斷。
3. **重新加入。** 獨立監看元件在飛行迴圈之外，只對當前顧問行程採取復原動作。SLM 的 `repair=restart` 在顧問異常退出後生效。`slmctl stop` 是正常停止，手動 `slmctl restart` 是明示的停止與啟動，應另行記錄。部署時確認 `slogger2` 和 SLM 可用，並避免 `FlightSW` 依賴 `MlAdvisor`。新連線獲新識別，載入、暖機並通過首筆新鮮有效推論後重新加入。記錄 SLM 的 backoff 及 `-R` 重啟限制，耗盡後由 FDIR 持續處置。 [QNX SLM](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html) · [QNX `slmctl`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slmctl.html)

`SCHED_SPORADIC` 的預算屬於**執行緒在正常優先權下的執行時間**，耗盡後可在較低優先權執行。把推論、OpenBLAS 與 IPC 的執行緒數和有效排程納入清單，優先使用容易列舉的單執行緒推論配置。CPU-time 計時器可偵測忙迴圈消耗，等待中的故障由經過時間監看偵測。QNX 8.0 也有 `RLIMIT_AS` 及 SLM `rlimit` 文件，原規劃的待查事項可更新為驗證目標映像的**虛擬位址空間**限制與配置失敗路徑，另記錄實體記憶體觀察。 [QNX Sporadic scheduling](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.sys_arch/topic/kernel_Sporadic_scheduling.html) · [QNX 執行時間監看](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.prog/topic/timing_execution_times.html) · [QNX `setrlimit`](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/s/setrlimit.html) · [QNX SLM](https://qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)

| 驗收順序 | 故障注入 | 判定條件 |
| --- | --- | --- |
| 主驗收 | ML 活著但不產出有效結果，例如 busy loop 或仍發 heartbeat | 量推論過期、回退與輸出。飛行工作符合第 2 節時限，備援決策與輸出可查驗。 |
| 主驗收 | ML 異常退出後重新加入 | Q1、Q2 使用同一異常退出。檢查 `FlightSW` 行程實例與週期持續，Q1 的新顧問經暖機及有效推論後重新加入。注入舊工作階段結果並查看拒絕理由。 |
| 元件驗收 | IPC 收件前停住或收件後不回覆，佇列滿載、重複或過期封包 | 以元件測試覆蓋阻塞和滿載，記錄丟棄、拒絕及回退。每週期工作量維持上限，重複建議只執行一次。 |
| 機制驗收 | 重複異常退出、CPU 競爭、位址空間上限或權限拒絕 | 驗證限速後仍能維持 FDIR。依宣稱的機制另外記錄有效優先權、超限配置結果及連線允許／拒絕。 |

## 4. 驗證 ML 的價值與恢復行為

### 實驗 A · 真實資料的片段偵測

使用 OPSSAT-AD **v2**，固定 DOI `10.5281/zenodo.15108715`、資料檔雜湊及取用方式。v2 隨附 MIT 資料授權，引用資料時保留作者與授權資訊。資料包含取自九個通道的 2,123 個人工切段，每段是單通道時序，提供正常／異常標籤和手工特徵。用 `dataset.csv` 的 `anomaly` 和 `train` 欄位重現切分。論文的訓練總數有誤植，依表 1 各類小計預期訓練 1,594、測試 529，下載後從固定版本 CSV 逐欄重算。 [OPSSAT-AD v2 資料](https://zenodo.org/records/15108715) · [資料授權檔](https://zenodo.org/records/15108715/files/LICENSE?download=1) · [資料論文表 1](https://arxiv.org/html/2407.04730v1#S2)

從訓練集劃分驗證資料，所有參數、正規化及閾值在訓練／驗證上定稿。固定測試集回報 AP、precision、recall、MCC 和主機／QNX 一致性。若與論文的 `AUC_PR` 數字比較，採作者範例中的 `average_precision_score` 定義。圖表標明「專家切段的異常分類」。 [作者的重現程式](https://github.com/kplabs-pl/OPS-SAT-AD/blob/main/modeling_examples.ipynb)

專家切段的長度、缺口與邊界會影響特徵。線上推論另外固定樣本時間尺度、因果視窗 `[t−W, t]`、步距、暖機、缺值與資料過期規則。訓練與評估沿用同一套因果前處理，缺樣另外記錄，視窗未達最低有效樣本時輸出「資料不足」。兩種實驗**共用顧問介面與推論執行環境**，各自記錄資料、特徵規格、權重版本及測試切分。閉迴路設定使用獨立模擬訓練／驗證劇本。若要沿用權重，先為觀測值與前處理建立對應，再測試轉移效果。 [OPSSAT-AD 方法與特徵](https://arxiv.org/html/2407.04730v1#S2)

### 實驗 B · 同一姿態感測情境的線上偵測與處置

**建議情境**　模擬其中一顆粗略太陽感測器（光電二極體）逐步偏移，使太陽向量估計劣化。每顆感測器由照入角、可視範圍、遮蔽與雜訊生成讀值。配置有重疊視野的感測器。從估計中去掉一顆前，檢查剩餘受光通道的幾何條件足以估計太陽向量，再用獨立的感測器一致性條件判定是否接受該動作。模擬器的真值由評估腳本使用，與 Gate 的輸入隔離。挑戰用語聚焦在**太陽向量估計恢復**，與感測器模型的能力一致。 [Basilisk 粗略太陽感測器模型](https://avslab.github.io/basilisk/Documentation/simulation/sensors/coarseSunSensor/coarseSunSensor.html) · [NASA SmallSat GNC](https://www.nasa.gov/smallsat-institute/sst-soa/guidance-navigation-and-control/)

| 比較組 | 運作方式 |
| --- | --- |
| 傳統 FDIR | 使用具持續性判斷的殘差或趨勢門檻，經相同的處置 Gate 和估計器。用模擬驗證組選參數，使兩種偵測器適用同一誤報事件上限。 |
| ML + Gate | 用固定的模擬模型處理因果視窗。ML 提出單通道隔離建議。Gate 用可獨立取得的感測器一致性、排除後的可觀測性、狀態及限頻確認動作是否可行。 |
| ML 故障後回退 | 用相同感測器故障與負載，在預定時刻讓 ML 不回覆或退出。觀察獨立 FDIR 和太陽向量估計繼續運作。 |

在正式測試前凍結故障起點與斜率、種子、誤報事件的分組方式、可接受的太陽向量角誤差、連續達標週期數及可比較的時間窗。至少納入正常姿態變化、短暫遮蔽或進入陰影，以及排除後受光幾何不足等反例。未知異常可先通知並啟用 FDIR。估計持續無效時，依獨立條件進入模擬的**子系統降級狀態**，加入維持時間與狀態控制，避免誤報造成反覆切換。ECSS 將整星安全模式的進入條件連到系統層級的關鍵功能，並將退出交由地面控制，建議據此調整原案「未知異常 → safe mode」的對應表。 [ECSS-E-ST-70-11C Rev.1 §5.7.5.6](https://ecss.nl/wp-content/uploads/2025/10/ECSS-E-ST-70-11C-Rev.1-%2815October2025%29.pdf)

以時間軸分別記錄**故障起點、首次有效警報、Gate 核准、處置生效及穩定恢復**。先核對 Gate 核准所用的條件與傳統偵測門檻是否相同。兩者相同時，先估計 ML 能帶來的預警價值，處置提早須靠獨立的動作可行性證據支持。保留感測器的偏移輸出，處置只移除該讀值。以估計與模擬真值的角誤差判斷是否連續數個週期回到容許範圍。報告漏報數、正常劇本的誤報事件率、正確／不必要／錯誤處置數、處置前後角誤差及恢復時間。將漏報與無法恢復的劇本明列，標記各延遲統計的有效樣本數。警報提前支持預警價值，處置與角誤差改善支持恢復價值。兩者皆無改善時，可報告已有證據支持的移植推論、拒絕及回退能力。
