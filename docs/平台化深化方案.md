# F Prime on QNX 平台化深化方案

**整理與補充** Codex，2026-11-19。此檔保存平台化深化原案。下文照錄原提案的部署與順序。現行實作邊界、時程、驗收及公開條件見 [v0.3 規劃書](專案規劃書.md) 和 [D20](決策與變更紀錄.md#d20--採用平台化並凍結工程驗收邊界2026-11-19)。

## 核心主張與交付邊界

**讓其他開發者能採用同一套 F Prime／QNX 移植層，並在參考任務中重現 ML 顧問失效時的時序、回退與重返。** 飛行迴圈要在事先宣告的截止時間內提交有效估計或降級狀態。恢復後，顧問憑新工作階段的第一筆有效結果重新加入。

用兩個部署完成證據。上游 F Prime `Ref` 驗證平台層可以支援既有部署，已在 QNX 8.0 x86-64 通過 GDS 往返及空目錄重建。ADCS 參考部署用一個完整任務驗證故障圍堵。ADCS 的時序、回退與重返要以各里程碑的 QNX 實測認定。 [M1 實測與 OSAL 支援範圍](實作迭代紀錄.md#i-05--codex-執行並診斷-qnx-客體的-osal-測試v1)

## 四層如何共同驗收

| 層次 | 交付內容 | 獨立 agent 可查的證據 |
| --- | --- | --- |
| QNX 平台層 | `FprimeQnx/` 的 CMake、工具鏈、POSIX OSAL 相容、`QnxTimer` 與需要的 QNX 驅動。固定 F Prime revision、支援架構與 SDK 版本。 | 上游 `Ref` 只套用列得出的移植差異即可建置，GDS 送指令後收到兩項事件和一項週期遙測。保存 V1 的失敗、跳過與不支援項。 |
| 故障圍堵執行層 | 共用有界交接、傳輸介面和 session／新鮮度檢查。飛行迴圈在交接區滿時依既定策略繼續，`IpcWorker` 處理可能等待的傳輸。SLM 負責異常退出後的重啟。 | UDP 基準與 QNX 原生 IPC 共用同一套上層行為驗收。可查滿載計數、舊結果拒絕、不同 PID 與新 session。把缺少新結果的偵測、程序退出及重啟各記成事件。 |
| ADCS 參考部署 | 一組 `FlightSW`／`MlAdvisor`、模擬感測器、估計器、傳統 FDIR 與 `RecoveryGate`。快照及提案契約可重用，ADCS 的處置白名單與估計有效性由任務層提供。 | 同一參考部署先用確定性回覆驗證介面，再接模型。可查顧問失效時 FDIR 接手、Gate 核准或拒絕的理由，以及新顧問交回有效結果。 |
| 可重現證據 | 沿用 `clean-rebuild.sh` 與 `osal-check.sh`。在 ADCS 驗收穩定後，依 v0.2 規劃用 `run-all.sh` 串起啟動、注入、量測與結果匯出。 | 固定版本、故障劇本、原始紀錄、重跑命令及判定條件。README、影片與 Codelab 共同引用同一輪結果。 |

共用層的取捨以兩件事檢查。上游 `Ref` 可以獨立採用 QNX 平台層，ADCS 可以在同一介面下更換傳輸與顧問實作。主驗收穩定後，先補短 trace、負載掃描和 Codelab。AArch64 依 v0.2 列為加分項，跨 RTOS、額外模型及通用管理介面列入賽後評估。

## 驗收順序

1. **先完成 M2 的雙行程基準。** 在 QNX 客體上驗證 UDP 快照與回覆，保留兩個 PID、快照序號與每週期時間戳。有界交接區滿載時要有計數，FlightSW 要持續提交。UDP 路徑通過後，再驗收 `QnxMsgDriver` 和 SLM。 [v0.2 元件與里程碑](專案規劃書.md)
2. **M3 跑同一條故障時間軸。** 名目運作時先記時序基準。個別注入顧問活著但停止產出及顧問異常退出。另送過期、重複或跨工作階段的建議，驗證 Gate 的拒絕理由。彙整故障注入、FDIR 接手、程序重新啟動、新 session 和首筆有效結果的時間點。 [時序契約與故障矩陣](專案規劃書.md#62-時序契約)
3. **以 Q1／Q2 歸因自動重返。** 同一 QNX 映像、二進位、負載、種子、注入時機與觀察窗，只切換 SLM 的 `repair=restart`／`repair=none`。兩組各自評估 FlightSW 時限、回退與重返。SLM 的重啟證據以異常退出為起點，仍在執行的顧問卡死由新鮮度逾時識別。基準可重跑後，再逐級增加 CPU 負載或請求率，找出觀察到的首次逾期。 [v0.2 對照組](專案規劃書.md#63-對照組與試驗設計) · [QNX SLM 文件](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)
4. **M4 驗證 ML 有何貢獻。** 以相同測試劇本、動作條件與事先凍結的誤報上限比較純 FDIR 與 ML 顧問介入。記錄預警、Gate 核准、處置生效與穩定恢復。保持 OPSSAT-AD 的離線推論一致性和 ADCS 閉迴路模擬各自的資料與結論。 [v0.2 AI 評估](專案規劃書.md#43-評估指標)
5. **M5 把同一份證據交給第三方。** 讓另一位開發者用自己的 SDK，從固定 commit 重跑 `Ref` 和 ADCS 的一條主故障劇本。Codelab 教讀者從重建到判讀時間軸。整理 OSAL 失敗的上游修正與回歸輸出，公開材料依既有授權確認流程處理。 [v0.2 上游貢獻與交件](專案規劃書.md)

### 每輪交付的最低資料

- **環境與劇本**。Commit、SDK、映像與 QEMU 配置、測試負載、種子、注入週期、觀察窗、`T`、`D` 和預先宣告的恢復門檻。
- **結果與分母**。用 `cycle_id` 和 `release_k` 列出應執行週期，按實際事件填上 `start_k`、`finish_k`、輸出狀態及 drop counter。總結逾期／應執行週期、p99、最差延遲、`T_fallback` 和 `T_rejoin`。漏期依第 6.2 節計為逾期，資料缺失到無法判讀的場次另行標記。報告結論限於實測的映像、負載、樣本數與觀察窗。
- **查證入口**。用 `run_id` 串起原始資料、判定、圖表與影片時間碼。影片先展示一次故障全程，README 讓評審能查原始結果與重跑指令。 [官方規則第 4、6 節](https://qnx.devpost.com/rules)

## 獎項與目標名次

下表是 Codex 的參賽目標。名次仍由最終送件、實測結果和其他作品決定。官方評分等權考量技術實作、設計、潛在影響、創新與 AI 創意。這個平台的關聯分別是目標端實作、單一完整任務、第三方可採用，以及 AI 出錯時仍受時序與處置條件約束。 [官方規則第 6、8 節](https://qnx.devpost.com/rules)

| 獎項 | 名次或名額及現金 | 這份作品的目標和所需證據 |
| --- | --- | --- |
| Open-Source Contribution & Ports | 組別第 1 名 US$4,000，第 2 名 US$2,000 | **首要目標是組別第 1，前二是合理的參賽目標。** 交付獨立平台庫、上游 `Ref` 重建、OSAL 支援表與可重跑的 ADCS 證據。 |
| Best Use of QNX-specific Technologies | 1 個得主，US$3,500 | **優先爭取的加碼獎。** 實測 QNX pulse、原生 IPC 和 SLM 各在任務中的作用，用 Q1／Q2 與時序紀錄交代恢復和時限。 |
| Best Codelab / Tutorial | 1 個得主，US$3,500 | **第二個加碼獎目標。** 讓讀者用自己的 SDK，完成建置、注入故障並讀出一條時序證據。依規則提交賽期內撰寫的教學 URL。 |
| Grand Prize | 全場 1 個得主，US$10,000 | **進階目標。** 需同時做到完整的 ADCS 示範、第三方可採用、可核對的故障測試，以及評審能快速理解的呈現。 |
| Honorable Mentions | 3 個名額，每個 US$1,000 | 額外的整體評選機會，依官方名額表列。 |
| Community Choice | 1 個得主，社群曝光與 QNX 周邊 | 額外的社群投票獎。 |

同一作品最多可得一個 Overall 獎、一個 Bonus 獎與一個 Community Choice。Grand Prize、組別名次與 Honorable Mention 都列在 Overall。兩個加碼獎可以共用準備材料，得獎上限是一項。最值得主攻的組合是 **Ports 第 1 名＋Best Use of QNX-specific Technologies**，合計現金 US$7,500。Ports 第 2 名搭配一個加碼獎為 US$5,500。 [官方獎項與兼得規則](https://qnx.devpost.com/rules)

## 交給其他 agent 的檢核

1. 從乾淨 checkout 驗證 `Ref` 只依賴平台層，並列出支援範圍和所用版本。
2. 檢查顧問卡死、退出、過期回覆各自的測試和原始資料。用分母、時間戳與配置檔獨立重算結果。
3. 對每個新增功能指出它服務的驗收或官方評分項。優先追蹤會阻礙 M2／M3 實測的相依問題，將新增範圍與採納決定記回決策紀錄。
