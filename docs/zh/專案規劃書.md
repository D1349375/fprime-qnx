## 1. 問題與論點(摘要)

1. 太空任務需要機上自主判斷;地面監控受下行排程限制【已查證:Telemanom 論文配合 SMAP 每 70 分鐘下行】
2. 傳統 FDIR 靠門檻,認不出緩慢劣化與未知故障【已查證:arXiv 2604.08424】
3. 機上 ML 卡在信任、認證、可解釋性,而且主流 ML 工具太重【已查證:arXiv 2604.08424、SmallSat 2026 mlpack 論文】
4. ML 元件本身會卡住、吃光 CPU、當掉,飛行軟體不能跟著掛

**論點**:QNX 的微核心隔離、即時排程、行程監控重啟,把 3、4 點變成可以工程化驗收的問題。**AI 是存在的理由,QNX 讓它可以被部署,F Prime 平台庫讓別人也能用。**

**採用對象**:QNX 不在 F Prime 官方已支援或規劃中的平台清單【已查證】;NASA Goddard 的 cFS 已支援 QNX 8.0【已查證】,F Prime 還沒有。首位採用者是「已有 F Prime deployment、想在 QNX 上跑既有應用並評估 ML 隔離」的飛行軟體整合者。

**產業標準對照**:
- **ECSS FDIR 分層**:第 0–2 層自主修復、第 3 層 safe mode、第 4 層 survival mode【已查證:Thales Alenia Space 簡報】。ECSS-E-ST-70-11C Rev.1 §5.7.5.6 把整星 safe mode 的進入連到系統層級關鍵功能、退出交給地面【已查證】,所以本案的 ML 建議最多到**子系統降級**,不觸發整星 safe mode(第 4.4 節)
- **ECSS 機上自主等級**:E2 地面預排程序,E3 事件驅動的機上自適應操作【已查證】
- **ASTM F3269-21 Run-Time Assurance**:複雜功能(本案的 ML)與確定性恢復功能並存,由安全監視器切換;恢復邏輯越簡單越好;同一任務反覆觸發恢復代表複雜功能有問題【已查證】

## 3. 系統架構

### 3.1 平台分層與採用邊界

參賽版本使用一個公開 repo，並保留 F Prime 的固定 submodule。F Prime 的平台貢獻流程要求平台庫與使用該庫的參考專案，官方支援還涉及文件、持續測試與維護。賽後再依貢獻流程評估拆 repo 或申請納入社群。[F Prime 平台貢獻指引](https://fprime.jpl.nasa.gov/latest/docs/user-manual/framework/supported-platforms/#how-to-contribute-a-new-supported-platform) · [F Prime 移植指南](https://fprime.jpl.nasa.gov/latest/docs/how-to/integrate/porting-guide/)

| 層 | 位置與交付 | 驗收 |
| --- | --- | --- |
| QNX 平台層 | `FprimeQnx/` 提供 CMake、qcc 工具鏈、POSIX OSAL 相容層、`QnxTimer` 與 `QnxMsgDriver`。 | `adoption/ref-qnx.patch` 列出上游 Ref 的採用差異，`scripts/clean-rebuild.sh` 驗收 GDS 往返。`scripts/osal-check.sh` 保留測試及不支援範圍。 |
| 故障圍堵執行層 | `FprimeQnxReference/Components/Link/` 及飛行側 I/O worker 提供有界交接、共用訊框、傳輸選擇及 session／新鮮度檢查。SLM 模板在 `FprimeQnxReference/qnx/`。 | UDP 與原生 IPC 共用上層驗收。顧問可以用確定性回覆或 ML 實作。M3 檢核故障偵測、資料拒絕和重返。 |
| ADCS 參考部署 | `FlightDeployment/`、`MlDeployment/` 以及任務元件負責感測器、估計、FDIR、Gate、處置與模型。 | M2 已交付雙行程與估計短測，M3 補故障圍堵，M4 用同一介面接實際模型。ADCS 的可觀測性及動作白名單留在任務層。 |
| 可重現證據 | 既有 M1 腳本、`scripts/m2-check.sh`、規劃的故障 runner／原始事件／報表與教學。 | 固定 commit、SDK、負載、判定與 `run_id`。M5 驗收從乾淨 checkout 重建 Ref，另重跑一條正式 ADCS 故障劇本。 |

兩條採用流程可獨立執行。跨 RTOS、第二個參考任務、新模型框架、通用管理介面及拆 repo 留到賽後評估。Ref 和 ADCS 各自依賴平台庫。ADCS 的顧問連線目前是任務範例內的共用骨架。可攜介面先由已實證的替換點和一份採用教學界定。

### 3.2 執行期架構（M3–M5 目標）

```
WSL2 Ubuntu 24.04(主機)                 QEMU x86_64 + KVM(QNX 8.0 精簡映像,無圖形介面)
┌─────────────────┐   TCP(virbr0 橋接)  ┌──────────────────────────────────────────────────┐
│ F Prime GDS     │◄──────────────────►│ slm(System Launch and Monitor)                   │
│ (網頁地面站)     │                     │  ├─ FlightSW   [secpol type: fsw_t]  critical     │
│ 指令 / 遙測 /    │                     │  │   QnxTimer → RateGroups(SCHED_FIFO 高)          │
│ 事件 / 圖表      │                     │  │   AdcsSim、SunEstimator、FeatureExtractor       │
└─────────────────┘                     │  │   RecoveryGate、RecoveryExecutor、TimingLog     │
                                        │  │   ┌──────── 有界交接區(SPSC,固定容量)───────┐ │
                                        │  │   │ 飛行迴圈:寫快照、讀合格結果,絕不等待     │ │
                                        │  │   └───────────────▲───────────────────────────┘ │
                                        │  │   IpcWorker 執行緒(server,name_attach)        │
                                        │  │        ▲ MsgSend / MsgReceive / MsgReply       │
                                        │  │        ▼  只收兩種型別:快照請求、推論結果     │
                                        │  └─ MlAdvisor  [secpol type: ml_t]  repair=restart │
                                        │      FfnClassifier、(KdeNovelty、Explainer)       │
                                        │      RecoveryAdvisor                              │
                                        │      SCHED_SPORADIC 預算 + QnxCpuBudget 監看       │
                                        └──────────────────────────────────────────────────┘
```

M2 已有雙行程、pulse 驅動被動 rate group、SCHED_FIFO、獨立通訊與紀錄執行緒、有界佇列及 SLM 測試模板。圖中的完整 Gate、FDIR、顧問預算、開機整合及 ADCS 專屬 GDS 事件是後續驗收項。Ref 的 GDS 驗收已有證據。[M2 結果](實作迭代紀錄.md#i-10--驗收-udp原生-ipc-與-slm)

**設計重點**
- **兩個行程**:`FlightSW` 與 `MlAdvisor`。官方多核心指南在 Linux 上用 named message queue 或 pipe 串 GenericHub【已查證】,我們換成 QNX message passing
- **飛行迴圈絕不等 ML**:`MsgSend` 是同步阻塞,所以飛行迴圈不直接呼叫 IPC。飛行迴圈只和**有界交接區**互動;`IpcWorker` 執行緒負責 `MsgReceive`/`MsgReply`。交接邊界放在 `GenericHub` 呼叫**之前**,因為 GenericHub 在呼叫 driver 前就取緩衝區並序列化【已查證:v4.4.2 GenericHub.cpp】;F Prime 預設 `PriorityQueue` 在 `NONBLOCKING` 路徑仍取 mutex【已查證】,所以交接區用固定長度、單生產者/單消費者、失敗即返回的設計,滿載時有明確捨棄策略與 drop counter
- **FlightSW 是 server**:`MlAdvisor` 以固定上限頻率請求快照、送回結果;推論在 ML 行程內執行。介面收斂成「遙測快照」「推論結果」兩種具型別資料,解碼前驗證版本、類型、索引與長度。指令分派器不跨行程
- **飛行軟體 critical**　部署模板已標示。QNX 文件定義 critical 行程死亡會使系統崩潰，實際重啟取決於目標平台組態。M2 測試移除了 critical 以便結束及取回資料。開機整合與 critical 行為需獨立驗證。FlightSW 的啟動和週期不依賴 MlAdvisor。[QNX SLM](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)
- **ML 設 `repair=restart`**　SLM 依元件的 `<SLM:repair>` 處理異常退出，backoff 為元件設定。SLM 的 `-R` 限制單位時間的復原嘗試頻率，官方文件的預設為每分鐘兩次。Q1／Q2 固定 `-R` 並在每輪使用全新的 SLM 狀態，遇到反覆退出另外驗證實際行為。
- **優先權**:QNX 訊息傳遞會讓收件執行緒繼承送件端優先權【已查證】,要實測 `IpcWorker` 的有效優先權不會壓過飛行迴圈
- **secpol(加分)**:`ml_t` 只能連 hub channel【語法已查證;規則待驗證】

### 3.4 顧問生命週期與交接規則

1. **可用**:每筆推論結果帶 FlightSW 發給該連線的**工作階段 ID**、**來源快照序號**與結果類型。有效結果包含「無異常、無動作」或一筆含目標與理由的建議。FlightSW 以自己記錄的快照取樣時間驗證新鮮度,拒絕跨工作階段、過期、重複、未發出序號或格式錯誤的封包;建議動作再交 Gate
2. **不可用**　崩潰、斷線或合格輸出進度逾時後，FlightSW 撤銷應用層 session，切換處置決策到傳統 FDIR。FDIR 的狀態持續更新，確保切換時可直接接手。判定依同一客體的單調時鐘和快照序號，以取樣、視窗和暖機設定訂進度期限。heartbeat 供診斷。連續不合規導致的 Gate 隔離另外記錄，隔離期間的解封依任務策略。
3. **重新加入**　FlightSW 發給顧問新 session，並在顧問交出第一筆新鮮有效結果後恢復其可用狀態。同 PID 停滯後恢復或重連也需重新協商，由 FlightSW 換代並拒絕舊結果。顧問異常退出時，SLM 依設定啟動替代行程。紀錄同 PID 重新協商、新 PID 重啟及操作員手動恢復的不同來源。
4. **兩種卡住**　顧問活著但停止合格輸出屬應用層進度停滯，FlightSW 按結果有效期進入回退。FlightSW 的 IpcWorker 收訊後未回覆屬傳輸故障，獨立檢查 unblock pulse、client 返回與飛行輸出。`name_attach` 建的通道帶 `_NTO_CHF_UNBLOCK`,收件後，REPLY-blocked client 的 kernel timeout 會向 server 送 unblock pulse，由 server 回覆或報錯後才解除阻塞。M2 驅動所設的 100 ms 是 timeout 設定值，正式硬上限仍待專門測試。[QNX name_attach](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/n/name_attach.html) · [QNX TimerTimeout](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/t/timertimeout.html)

### 3.5 資料流（一次完整的偵測到恢復）

                                                                  │ FfnClassifier → RecoveryAdvisor
GDS ◄─ 事件:核准/拒絕(規則編號、session、序號)◄─ RecoveryGate ◄─ 交接區 ◄─ IpcWorker ◄─[MsgSend 結果]

### 4.4 恢復建議與 Gate 規則

**建議動作表**

| 偵測情況 | 建議動作 | 對應 |
|---|---|---|
| 單一光電二極體偏移／卡值 | 使用顧問或獨立殘差提出候選通道，經共用 Gate 驗明幾何與一致性後排除，保留原始讀值。 | ECSS 第 1–2 層 |
| 磁力計某軸卡值或偏移 | 重置;仍異常則標記不可用 | ECSS 第 1–2 層 |
| 多通道異常、不明原因,或估計持續無效 | 通知 + 啟用 FDIR;依獨立條件進入**ADCS 子系統降級狀態**(有最短維持時間,避免來回切換) | 子系統層;整星 safe mode 不由 ML 觸發 |
| 顧問失聯或被隔離 | (不由 ML 建議)Executor 退回門檻 FDIR | — |

**RecoveryGate 規則**(確定性、刻意簡單)
1. **白名單**:只接受上表動作
2. **新鮮度與工作階段**:session ID 必須是當前工作階段,來源快照序號必須是已發出且未過期的序號;重複封包只執行一次
3. **持續性**:同一異常連續 N 次偵測才受理
4. **限頻**:同一動作在時窗 T_w 內最多 K 次
5. **可觀測性**:排除後以有效量測與通道方向檢查估計是否仍可觀測。六個 ±軸 cosine 感測器在理想直射下，同時間至多三顆有正的直接照度。實驗 B 的成功劇本加入斜向冗餘感測器，確認排除故障通道後可用的量測方向仍獨立且條件數符合門檻。幾何不足的反例須拒絕排除並提交降級狀態。凍結角誤差上限和穩定維持窗，以模擬真值評分。[Basilisk 粗略太陽感測器模型](https://avslab.github.io/basilisk/Documentation/simulation/sensors/coarseSunSensor/coarseSunSensor.html)
6. **獨立一致性**:用不依賴 ML 的感測器一致性條件確認該通道確實偏離
7. **永遠允許更安全的動作**:進入子系統降級不受限頻約束
8. **顧問隔離**:時窗內被拒超過 M 次 → 隔離 ML,退回 FDIR
9. **全部留紀錄**　每個核准或拒絕都寫入目標端驗收事件，附規則編號、session 和序號。GDS 從非即時旁路呈現，另記展示資料是否掉包。

N、T_w、K、M 在模擬驗證組上定稿,正式測試前凍結並寫入決策紀錄。

### 6.2 時序契約

`T = D = 20 ms` 是 M2 試跑基準。正式試驗前固定週期、截止時間、工作負載、顧問結果有效期、暖機、注入位點、觀察窗、回退與重返門檻，並記錄選擇理由。先用獨立的試跑確認記錄與配置，再凍結正式設定。M2 的 250 ms 結果有效期與 1 s SLM backoff 是起始組態。正式門檻由所用取樣視窗、下一次飛行釋放、重啟與模型暖機預算決定，報告時保留值及設定版本。

| 欄位 | 定義 |
| --- | --- |
| `release_k` | `t0 + k × T`，`k = 0 … N−1`。從事前固定的 t0 與 N 產生應執行週期。 |
| `start_k`、`finish_k` | 同一 QNX 客體 `CLOCK_MONOTONIC` 的實際開始、有效估計或降級狀態提交給下一階段的時間。若提交走有界介面，記錄提交成功或失敗。M2 在估計更新處量測。M3 在飛行側估計接收元件確認成功接收該週期的估計或降級輸出後取時。凍結適用劇本的角誤差、資料過期和降級內容判定。 |
| 延遲與逾期 | Recompute p50, p99, the maximum and minimum deadline margin for release-to-start and release-to-commit timing. Count an absent or late submission as a miss. Use all scheduled cycles as the denominator. Keep the measurements and counts in local evidence. |
| `T_fallback` | 故障注入生效 → 首次由 FDIR 決策且有效估計或降級狀態已提交。記錄最近合格輸出的取樣與有效期、回退切換原因、提交事件。 |
| `T_rejoin` | 故障注入生效 → FlightSW 首次接納新 session 的新鮮、具有效格式且能與快照對帳的結果。無異常回覆也可完成重返。Gate 是否准執行處置另外記錄。 |
| 主驗收 | Apply the fixed per-cycle deadline and retain every missed or unresolved cycle and the full denominator in local evidence. Verify the expected output, rejection behavior, fallback and any expected rejoin against the declared criteria. Record no rejoin when Q2 reaches the end of its observation window without a valid result from a new session. Public findings describe the observed behavior and test scope under §9.4. |

在目標端記錄實際故障生效、FDIR 回退、程序退出或替換 PID、新 session 與首次有效結果，並記下事件的來源與時鐘。若外部注入工具無法在確切生效點取時，保留生效區間。到期驗收使用最早可能生效時刻計上界，若上下界分跨門檻，標記該次量測無法判定。正式回退與重返時間依上述事件重算。已知輸出確未提交的週期計為逾期。

Mark the run inconclusive when record loss or an incomplete timeline prevents a verdict. Keep the original result in local evidence and rerun the scenario.

### 6.3 對照組與試驗設計

| 組別 | 設定 | 層級 |
| --- | --- | --- |
| Q0 | 傳統 FDIR 基準。相同負載與任務工作量，關閉顧問。用途與實驗 B 的偵測效果比較分開記錄。 | 應做 |
| Q1 | 以 `repair=restart` 啟動顧問，注入同一異常退出。FlightSW 不受故障注入控制。 | 必做 |
| Q2 | 只把顧問的修復策略改為 `repair=none`。固定映像、二進位雜湊、種子、暖機、負載、注入時機及觀察窗。 | 必做 |

先交錯執行 Q1／Q2 與無故障基準。每輪固定 SLM 復原頻率並使用新 SLM 狀態，避免前次復原嘗試影響結果。必要情境各至少 10 次，Q1／Q2 各至少 10 輪。再各自注入活著但停止輸出、過期／重複／跨 session 結果與不合規提案。顧問卡住時先驗證 FDIR 與時限。若採用主動監看並需要比較重啟，兩組用相同的終止條件和事件，再只變更 SLM 的修復策略。原生路徑的必要傳輸故障另安排 server 收件後暫停回覆，由獨立控制在固定時間解除。分開判定飛行是否守時、client 是否返回、服務何時重連。通報卡住期間的實際返回狀態及條件。

每輪由 `run_id` 串起固定 commit、SDK、映像與 QEMU/KVM 配置、vCPU／記憶體、負載與種子、劇本、時間戳、佇列丟棄、PID／session、拒絕規則與輸出。基準可重跑後，可逐級增加單一 CPU 負載或 IPC 請求率，並記錄首次觀察到逾期的配置與樣本數。結果限於實測虛擬機與場景。Q1／Q2 的因果主張指向 SLM 設定對顧問恢復的差異，兩組各自的飛行時序由原始週期記錄驗證。

## 16. Codex 深化提案

**提出者** Codex。**日期** 2026-11-19。以下保留 v0.2 的提案及當時的檢核問題。第 3、6、9、10、11 節與 D20 是 v0.3 的現行規格。 [決策 D16](決策與變更紀錄.md#d16--收錄-codex-深化提案)

平台分層、上游 `Ref` 與 ADCS 的採用證據、故障重跑契約及獎項目標的原始提案已移出公開 repo，現行規格以本文第 3、6、9、10、11 節與 D20 為準。

**提出依據** M1 已在 QNX 8.0 x86-64 實測 Ref/GDS 往返和從空目錄重建。V1 共 247 個測試通過、11 個失敗、1 個跳過。這些結果支持繼續做 M2 雙行程。ADCS 的時序、顧問恢復與 ML 效益需由後續任務實驗驗證。 [M1 實作與證據](實作迭代紀錄.md)

### 16.1 完整交付順序

| 階段 | Codex 建議的完整成果 | 可檢核的證據 |
| --- | --- | --- |
| M2 雙行程 | 用可重現的 ADCS 輸入先跑通 QNX 上的 `FlightSW` 和 `MlAdvisor`。沿用既定 UDP → `QnxMsgDriver` 的順序，讓兩種傳輸共用有界交接區與推論回覆契約，再接 SLM。先用確定性的顧問回覆驗證介面。 | 兩個不同 PID、請求與回覆可由快照序號串接、客體上的 `release_k`／`start_k`／`finish_k`、輸出有效性與 drop counter。顧問關閉或交接區滿時，飛行迴圈仍持續提交。 |

### 16.2 深化時序與恢復證據

1. Interleave Q1 and Q2 with the image, workload, seeds, injection, warm-up and observation window fixed. Record the full planned denominator, missed cycles, p99, worst latency and minimum deadline margin in local evidence. Timestamp the process restart, new session and first valid inference to distinguish SLM restart from application recovery.
2. After reproducing the baseline, vary either the competing load on the same vCPU or the IPC request rate. Record the first observed failure configuration, sample sizes and repeated runs locally. Use a short, separately identified trace when investigating scheduling or blocking.
3. 把「仍發 heartbeat 但停止推論」和「重啟後收到舊 session 的延遲回覆」納入反例。核對回退、拒絕及再次可用的時間線，並確認新 session 回傳「無異常」也能成為第一筆有效結果。先各自量測單一故障，再做一輪組合故障。

### 16.3 深化 ML 對照與平台回歸

- **同誤報上限的 ML 對照** 在獨立驗證種子上凍結閾值和誤報上限。測試保留健康遙測、短暫遮蔽、慢速偏移、排除後幾何不足等劇本。用配對劇本比較預警時間與恢復結果，分開記錄警報提前與實際處置提前。
- **OSAL 可攜性** 先拆 Task 優先序和 RawTime 的測試修正。前者從目標有效範圍算出預期優先序，後者讓參考界線與被測時間使用同一時鐘及精度。另分開處理可寫掛載點 fixture 和 death test 的訊息比對。每項保留原失敗輸出，並用同一份變更跑 QNX 目標端與 Linux 主機回歸。 [原始失敗與客體診斷](實作迭代紀錄.md#i-05--codex-執行並診斷-qnx-客體的-osal-測試v1)
- **加分項排序** 主驗收可重跑後，先補能說明時序或圍堵結果的短 trace、sporadic 預算對照，以及能讓第三方重現的 Codelab。若資源足夠，再接唯讀 resource manager、secpol 和 AArch64 驗證。各項依第 11 節原有層級追蹤。

### 16.4 其他 agent 的檢核重點

1. 用現行 V1–V7 和 M2–M5 核對 §16.1 的證據，標出已涵蓋的要求、候選新增工作與可能重複的項目。
2. 檢查 Q1/Q2 是否只切換一項設定，以及時間戳、漏期分母、觀察窗和重返定義能否由原始資料重算。
3. 檢查實驗 B 是否使用獨立校準與測試種子，以及兩組比較是否共用故障劇本、Gate 和動作條件。
4. 核對 OSAL 的四類歸因並挑戰替代解釋。對每個要採納的新增項目，給出最小重現、驗收門檻及對主線時程的影響，再記入決策紀錄。
