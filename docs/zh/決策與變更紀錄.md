### 調研發現(影響後續設計)

- 提出三個 AI 方向:A 可被關住的機上 AI(建議核心)、B 建議恢復動作(延伸)、C 地面 LLM 助理(可選呈現層)

### D3:AI 核心採用 A + B
- **A 可被關住的機上 AI**:飛行軟體與 ML 分屬兩個 process,經 GenericHub 的 QNX message passing 傳輸層溝通;ML 用真實太空遙測(OPSSAT-AD、SMAP/MSL)做異常偵測並輸出可解釋結果;ML 受 SCHED_SPORADIC / rlimit 限制,失控時飛行軟體不受影響、ML 自動重啟
- **B 建議恢復動作**:ML 提出恢復建議,須通過飛行軟體端的確定性安全規則才執行(simplex / runtime assurance)
- **C 地面 LLM 助理**:本次未採用
- 細節見已移出公開 repo 的 AI 深化調研第 3 節

### D4:專案規劃書 v0.1 的設計決定(等使用者審閱)
完整內容見 `專案規劃書.md`。以下是規劃書採用、可以被推翻的決定:
1. **單一 repo `fprime-qnx`**(平台函式庫 + 參考專案 + ML),F Prime 用 submodule 引用;賽後再依官方慣例拆成兩個 repo。理由:Devpost 只收一個 URL,規則要求 repo 包含所有原始碼
2. **行程內 `Os::Queue` 不用 QNX MsgSend**:F Prime 佇列是非同步,MsgSend 是同步,語意不合;QNX message passing 用在跨行程 hub(`QnxMsgDriver`)
3. **QNX 用精簡無介面映像(mkqnximage)**,不用 Developer Desktop。理由:電腦只有 7.9 GB RAM
4. **ML 只用 mlpack 一套**(FFN 監督式 + KDE 非監督 + 遮蔽法解釋),onnxruntime 當備案
5. **主要資料集 OPSSAT-AD**(CC BY 4.0);SMAP/MSL 授權不明,只做內部比較、不放進 repo
6. **方向 B 依 ASTM F3269-21 RTA 架構與 ECSS FDIR 分層設計**,RecoveryGate 規則刻意保持簡單
7. **時序實驗在虛擬機內做,只主張相對差異**,並在 Limitations 誠實揭露

### D17 · 把飛行迴圈與顧問通訊分到不同執行緒（2026-11-19）

- 選擇兩個由 FPP 產生拓撲的部署，按規劃先驗 UDP，再替換傳輸層。編譯失敗後以 FPP 拓撲取代手接 port，讓接線配合 F Prime v4.4.2 的 direct calls。
- 飛行迴圈走 20 ms 的絕對單調時鐘時基，同步更新估計。通訊用獨立 worker。快照和回覆各用 4 格單寫者、單讀者佇列，滿載丟棄新項目並計數。另用 256 格交給 CSV writer，以避免阻塞等待或在飛行執行緒寫檔。週期編號按預定釋放時刻推算，便於核對缺號。
- 顧問以固定門檻、同一 session 和 cycle 產生可對帳的回覆。回覆以原始快照時刻限制在 250 ms 內。更換 session 或資料過期時清除現用建議。完整推論、恢復動作與負載驗證依後續里程碑。見 [I-08](實作迭代紀錄.md#i-08--建立雙行程udp-與飛行時序基準)。

### D18 · 沿用 GenericHub 訊框並增加 QNX 原生 transport（2026-11-19）

- UDP loopback 保留為可執行的基準。原生模式以 `name_attach/name_open` 和同步 Send／Receive／Reply 取代 UDP，兩種模式共用訊框、序號、ACK 及時效判定。原生驅動只在 I/O 路徑使用，飛行週期維持有界佇列交接。
- 驅動檢查訊息類別及邊界，斷線時回收 server connection。為 receive、send/reply 設定 100 ms 核心 timeout。QNX named channel 在服務端接收後由服務端控制 reply，失去服務時的完整行為與核心排程壓力需獨立量測。 [QNX TimerTimeout](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.lib_ref/topic/t/timertimeout.html)
- UDP 和原生模式已於同一套 QNX 客體組態完成各 200 週期的驗收，可作為接上模型與壓力測試的基準。 [I-10](實作迭代紀錄.md#i-10--驗收-udp原生-ipc-與-slm)

### D19 · 用 SLM 啟動依賴及重啟顧問（2026-11-19）

- 模板先啟動 flight，等待 QNX named channel，再啟動依賴 flight 的 advisor。採用 `repair=restart` 和 1 秒 backoff，讓顧問可取得新 PID 和 session，並留出足夠測試時間觀察舊建議過期。
- 部署模板以 `critical` 標記 FlightSW。驗收腳本產生可正常停止的測試配置。故障注入只終止當輪由 SLM 啟動的 advisor PID，保留 FlightSW 的連續週期、用來對帳的顧問日誌、SLM 狀態與退出證據。啟動映像整合、critical 行為與 Q1/Q2 等條件對照留待後續驗證。 [QNX SLM](https://www.qnx.com/developers/docs/8.0/com.qnx.doc.neutrino.utilities/topic/s/slm.html)
- 目標端已實測單次自動重啟。Flight PID 未變、工作階段換新，以及新建議重新出現的時間順序均可從代理日誌與逐週期紀錄對照。 [I-10](實作迭代紀錄.md#i-10--驗收-udp原生-ipc-與-slm)

Case verdicts keep the original checkers and the [D70](#d70--pre-register-the-e13-classification-and-decision-rules-2026-11-24) labels. Tracing is on, so this round does not revise the D79 cost labels. With `insufficient` the round stops, and any further round needs the owner's decision.
