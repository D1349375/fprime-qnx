## 2026-11-12

### D1:賽道選 Open-Source Contribution & Ports
- 條件:不走實機(用 QEMU)、本機不跑大型模型
- 理由:11/12 公開投稿中 Ports 類只有 4 件,競爭明顯少於 Tooling(約 40 件)
- 依據:`歷屆得獎作品調研.md` 第 4 節

### D2:移植專案選 NASA F Prime
- 候選比較見 `Ports候選專案.md`(F Prime / sherpa-onnx / acados)
- 理由:社群慣例是平台移植獨立成 repo,跟比賽規則一致;OS 抽象層能對應 QNX 原生機制,有利於 Best Use of QNX-specific Technologies;QEMU 就能完整 demo;對本機運算負擔低
- 使用者附帶要求:**為了得獎,要把 AI 的部分深化並補齊**(F Prime 本身的弱點)→ 調研見 `AI深化方向.md`

### 調研發現(影響後續設計)
- F Prime 官方已有 mlpack 機上 ML 參考實作(fprime-mlpack-reference)和 SmallSat 2026 論文;mlpack / armadillo / ensmallen / onnxruntime 都已在 qnx-ports
- **QNX 8.0 不支援 adaptive partitioning**(官方 IDE 文件),限制 ML 的 CPU 用量改用 SCHED_SPORADIC / runtime clock / rlimit
- 提出三個 AI 方向:A 可被關住的機上 AI(建議核心)、B 建議恢復動作(延伸)、C 地面 LLM 助理(可選呈現層)

### D3:AI 核心採用 A + B
- **A 可被關住的機上 AI**:飛行軟體與 ML 分屬兩個 process,經 GenericHub 的 QNX message passing 傳輸層溝通;ML 用真實太空遙測(OPSSAT-AD、SMAP/MSL)做異常偵測並輸出可解釋結果;ML 受 SCHED_SPORADIC / rlimit 限制,失控時飛行軟體不受影響、ML 自動重啟
- **B 建議恢復動作**:ML 提出恢復建議,須通過飛行軟體端的確定性安全規則才執行(simplex / runtime assurance)
- **C 地面 LLM 助理**:本次未採用
- 細節見 `AI深化方向.md` 第 3 節

### D4:專案規劃書 v0.1 的設計決定(等使用者審閱)
完整內容見 `專案規劃書.md`。以下是規劃書採用、可以被推翻的決定:
1. **單一 repo `fprime-qnx`**(平台函式庫 + 參考專案 + ML),F Prime 用 submodule 引用;賽後再依官方慣例拆成兩個 repo。理由:Devpost 只收一個 URL,規則要求 repo 包含所有原始碼
2. **行程內 `Os::Queue` 不用 QNX MsgSend**:F Prime 佇列是非同步,MsgSend 是同步,語意不合;QNX message passing 用在跨行程 hub(`QnxMsgDriver`)
3. **QNX 用精簡無介面映像(mkqnximage)**,不用 Developer Desktop。理由:電腦只有 7.9 GB RAM
4. **ML 只用 mlpack 一套**(FFN 監督式 + KDE 非監督 + 遮蔽法解釋),onnxruntime 當備案
5. **主要資料集 OPSSAT-AD**(CC BY 4.0);SMAP/MSL 授權不明,只做內部比較、不放進 repo
6. **方向 B 依 ASTM F3269-21 RTA 架構與 ECSS FDIR 分層設計**,RecoveryGate 規則刻意保持簡單
7. **時序實驗在虛擬機內做,只主張相對差異**,並在 Limitations 誠實揭露

### 調研新發現(11/12)
- QNX 官方有「qsti-qemu-on-wsl」和「apk-based-cross-compile」兩份 codelab,分別解決 WSL 跑 QEMU、qcc 連結 apk 套件的問題
- F Prime 的 Linux 平台 = Posix OSAL + Linux 版 Cpu / Memory;`LinuxTimer` 用 timerfd(QNX 沒有)→ 需要寫 `QnxTimer`
- **QNX 不在 F Prime 官方已支援或規劃中的平台清單**;官方有新平台貢獻流程
- 電腦規格:7.9 GB RAM、i5-7200U 2 核 4 緒、WSL 未安裝

### D8:原開發主機 W1 環境設定
